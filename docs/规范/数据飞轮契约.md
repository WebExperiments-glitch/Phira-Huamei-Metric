## 1. 为什么做这个

P.H.M. 现在的瓶颈不是模型，是**标签**。

官谱留一法自检 0.819 ≈ 留出验证 0.827 —— 两个数字几乎相等，意味着模型已经把
「谱师标的定数」里能榨的信息全榨干了。剩下的方差里「谱师是谁」占 **83%**
（扣掉单例组噪声后约 **30%**；结构本身只解释 38%），**再换模型、再加特征都不会变好** ——
那部分是人的标注习惯与历史路径依赖，不是谱面的性质。

⚠ 但**别指望拿它做修正**：谱师先验实测**学不到**（加进去误差不降反升），
所以换模型的希望不在「加谱师特征」，而在**换一个更干净的因变量** ——
也就是本文件 §1 说的那条路。实测见
[审计补充-基线与天花板.md](../结果/审计补充-基线与天花板.md) 与
[谱师先验可行性.md](../结果/谱师先验可行性.md)（负面结果）。

要往下走，只能换一个更干净的因变量。「一万个人在这张谱上各丢了几分、丢在哪」
是实测数据，不是主观估计 —— 这是唯一的路。

**飞轮长这样：**

```
用户  →  玩谱（谱面来自 Phira 官方）
      →  客户端记录每一个音符的判定
      →  结算时上传到 huamei
      →  服务端聚合出「哪一段最容易失分」
      →  用它反推「这张谱应该是什么定数」
      →  回到 P.H.M.，成为比官谱定数更准的参照
```

## 2. 架构

```
┌─────────────────────────────┐
│  phira-huamei（桌面客户端）  │  GPL-3.0 派生自 Phira 0.8.2
│  · 只登 huamei 账号          │
│  · 所有网络请求打我们域名     │
└───────┬─────────────┬───────┘
        │             │
   读（取谱）      写（成绩）
        │             │
        ▼             ▼
┌──────────────────────────────────────┐
│  phm.app.workbuddy.host              │
│  /api/phira/*  透明代理 → Phira 官方  │  服务端代持 token
│  /api/hm/auth  登录（复用现有账号体系）│
│  /api/hm/play  收成绩                 │
└──────────────────┬───────────────────┘
                   ▼
            云数据库（Postgres）
```

**四个部件、三条边界。** 关键约束：

- 客户端**不直连** Phira，也**不知道** Phira 的 token —— 那是服务端的凭据。
- 客户端**不直连**数据库 —— 只有 HTTP 一条路。
- 服务端**永远信任客户端有限**（见 §8）。

## 4. 登录（客户端侧）

复用现有账号体系（WorkBuddy 云服务，Supabase 兼容 REST）。客户端不做任何新账号系统。

```
POST {CLOUD}/auth/v1/otp          { email }                  → 发验证码
POST {CLOUD}/auth/v1/verify       { email, token, type:"email" } → 拿到 access_token
POST {CLOUD}/auth/v1/token?grant_type=password                → 密码登录，拿 access_token
```

拿到 `access_token` 后，客户端**所有对 `/api/hm/*` 的请求**都带：

```
Authorization: Bearer <access_token>
```

服务端用它换 `auth.uid()`，作为 `owner_id`。**这就是「huamei 账号」。**

## 5. 取谱（服务端代理）

客户端把 `phira/src/client.rs` 的 `API_URL` 指到 `{PHM}/api/phira`，
其余代码**一行不改** —— Phira 的整个 API 调用面就全部走代理了。

服务端行为：

- `/api/phira/<path>` → `https://api.phira.cn/<path>`（超时 15s，重定向按白名单跟随）
- **剥掉**客户端带来的 `Authorization`，换成服务端自己的凭据（若有）。
  ⚠ 绝不能把用户的 huamei token 转给 Phira —— 那是泄漏。
- 只放行**只读**方法（GET/HEAD）。写操作一律 403。
- 响应按只读缓存 5 分钟（`/chart`、`/user` 这类元数据）。

> 白名单与重定向策略复用 `lib/review.mjs` 已有的实现
> （`FILE_HOSTS = {phira.5wyxi.com, phira-cdn.5wyxi.com}`，MAX_HOPS=3）。

⚠ **为什么需要服务端代持凭据**：部分谱面要登录 Phira 才可读。
把「浏览用凭据」放服务端，用户就只需要一个 huamei 账号。

## 6. 上报契约（← 本文件最重要的部分）

### 6.1 端点

```
POST {PHM}/api/hm/play
x-hm-token: <huamei access_token>      ← 【主用这个】
Authorization: Bearer <同上>            ← 兜底，别依赖它
Content-Type: application/json
```

> ⚠⚠ **为什么用自定义头 `x-hm-token` 而不是 `Authorization`**
>
> 2026-10-11 实测：同一把真 token，**本机整条链全绿、线上每一步都 401**。
> 逐层排查后定位到 —— **托管边缘会往入站的 `Authorization` 头里塞自己的东西**：
> 服务端收到的值长度 **379**，而真实 token 只有 **359**，且解析出来根本不是 JWT。
>
> 这一个原因同时解释了两件事：
> 1. 服务端拿它去调云端 `/user/me` 换身份 → 必然失败（带过去的是别的值）；
> 2. 降级路径本地解 JWT → 报 `no_sub`。
>
> 换成自定义头后，实测立刻通过，且 `verified: true`（走的是**云端正路**）。
> **凡是经过这个域名的自定义请求头都不受影响，只有 `Authorization` 被动了。**

### 6.1.1 身份是怎么定的（信任边界）

服务端优先调云端 `GET /.cloud/auth/v1/user/me` 换 `sub`（**正路**，返回里
`verified: true`）。从沙箱发出的请求还额外要求：
`x-wb-webapp-access-key` 头 + **`Referer` 或 `Origin` 至少一个**
（依据：`phm-web/lib/cloud.mjs` 顶部「身份由 referer 判定」；用真 token 实测过，
不带这两个头必然 `invalid_grant: the session is invalid, expired or issued for
another client` —— ⚠ 那句措辞有误导性，听着像 token 有问题，其实是**我们没报身份**）。

正路全挂才降级到**本地解析 JWT 取 `sub`**（返回里 `verified: false`）。
⚠ **降级意味着身份可伪造** —— token 是 HS256，密钥在服务端，我们**无法验签**，
只能校验结构 / `aud` / `exp`。影响面：可能有人把假成绩挂到别人名下；
不涉及任何隐私数据读取，且个体数据本就不可信（§8）。

### 6.2 请求体

```jsonc
{
  "client_ver": "0.8.2-huamei.1",   // 客户端版本
  "judge_ver": 1,                    // 判定数据格式版本（见 6.3）
  "chart_id": 22681,                 // Phira 谱面 id（必填；没有就别上传）
  "chart_level": "IN",               // EZ / HD / IN / AT
  "chart_digest": "sha256:9f2c…",    // 谱面文件字节的 sha256，防「改谱刷分」
  "chart_notes": 900,                // 客户端认为的物量（与谱面对账用）

  "score": 987654,
  "accuracy": 0.9821,
  "max_combo": 880,
  "counts": [880, 15, 3, 2],         // [perfect, good, bad, miss]
  "speed": 1.0,
  "mods": 0,

  "started_at": 1760257890123,       // Unix 毫秒，开谱时刻
  "finished_at": 1760258034265,

  "judge": "<base64 紧凑二进制，见 6.3>"
}
```

### 6.3 `judge` 紧凑编码（判定数据格式 v1）

**为什么不用 JSON 数组**：一盘 IN 有 900 个音符，JSON 对象约 60 字节/条 = 54 KB；
紧凑编码 8 字节/条 = 7.2 KB，base64 后 9.6 KB。省 5.6 倍，且解析零歧义。

```
偏移  类型        字段
─────────────────────────────────────────────
 0    u8          格式版本 = 1
 1..  [记录] × N   每条 8 字节，按时间升序
─────────────────────────────────────────────
每条记录（小端）：
  +0   u16   line_id     符在 chart.lines 里的下标
  +2   u16   note_id     符在该线 notes 里的下标
  +4   i16   offset_ms   判定时刻 − 音符时刻，毫秒，钳到 ±32767
  +6   u8    judgement   0=Perfect 1=Good 2=Bad 3=Miss 4=Hold按下
  +7   u8    flags       保留，填 0
```

**来源与语义（可直接对着源码核）**：

| 字段 | 来源 | 说明 |
|---|---|---|
| `line_id` | `prpr/src/judge.rs:564` 对 `chart.lines` 的 `enumerate()` | 就是 `chart.lines` 的下标 |
| `note_id` | 同上，`line.notes` 的下标 | `(line_id, note_id)` **唯一**标识一个音符 |
| `offset_ms` | `judge.rs:347` `commit(..., diff)` 的 `diff` | ⚠ 上游把它丢了，我们改了 `commit` 保留（见 §7） |
| `judgement` | `judge.rs:281` `Judgements` 的 `Result<Judgement,bool>` | 见下 |

⚠ **两处极易搞错的地方**：

1. `Judgements` 里的 `Ok(Judgement)` 才是**真判定**；
   `Err(bool)` 是 **Hold 的「按下」事件**（`judge.rs:627/689`），
   带着「是否落在 Perfect 窗口」的 bool。
   **它不是失误** —— 当成失误会让每个 Hold 都污染热力图。
2. 客户端**不上传**「点空了」的幽灵点击。Phira 本身不记录也不扣分
   （`judge.rs:605-612` 找不到音符就 `continue`），我们保持一致。

**服务端不需要客户端传时间轴** —— `line_id`/`note_id` 已经能唯一定位音符，
服务端拿自己的谱面副本即可还原「第几秒」。这也是 `chart_digest` 存在的意义：
digest 不一致 = 谱面被改过 = 这条数据不可信。

### 6.4 响应

```jsonc
{ "ok": true, "play_id": 12345, "is_pb": true }        // 200
{ "ok": false, "error": "chart_not_found" }            // 404
{ "ok": false, "error": "digest_mismatch" }            // 409 ← 谱面被改过
{ "ok": false, "error": "rate_limited" }               // 429
```

### 7.2 为什么要在 `take_input` 里洗文本（第 8 处）

**Windows 上输入框回传的文本是坏的。** 它由 `inputbox` crate 跑 PowerShell +
WinForms 弹原生窗，而 Rust 侧取的是 **`output.stdout` 的全部内容**：

```rust
Some(String::from_utf8_lossy(&output.stdout).trim_end().to_string())
```

实测 PowerShell **按 UTF-16 LE（带 BOM）写出**，原始字节：

```text
ff fe | 70 00 79 00 72 00 | 0d 00 0a 00
 BOM  |  p \0  y \0  r \0 |  \r \0 \n \0
```

按 UTF-8 读就变成 `\u{FFFD}\u{FFFD}p\0y\0r\0…` ——
**每个字符后面多一个 NUL，长度接近翻倍**，屏幕上完全看不出来。

症状：用户输入 `pyrpansiyuan123456@qq.com`（18 字符的 local），
程序报「**@ 前面有 59 个字符**」。

**放 `take_input()` 而不是各调用点**：它是**所有**文本输入的唯一出口
（设置页、谱名编辑、搜索、房间地址…），每条都会中同样的招。洗一次，全站生效。

⚠ 只清 `\0` / `U+FFFD` / 尾随 `\r\n` 三样 —— 用户打不出来，删掉只有好处。
**空白不在这里动**（搜索词、谱名里的空格合法），要删空白的场合自己去做
（邮箱在 `phira::huamei::normalize_email`）。

⚠ 尾随 CRLF 必须单独处理：crate 本来用 `trim_end()` 想删它，
但**末尾是 `\0` 不是空白**，所以它一个字符都没删掉。

### 7.1 为什么要把 assets 编进 exe（第 7 处）

上游用 macroquad 的 `load_file("assets/...")` 读资源，而
**这个 macroquad fork 没有自定义文件加载钩子**（`macroquad::file` 只有
`set_pc_assets_folder`）—— 拦不住那 77 个读取点（贴图/音频/字体/图标）。

于是 exe 必须和 `assets/` 目录待在一起；用户双击单独的 exe 会得到：

```
Couldn't load file assets\phigros.ttf: IOError(Os { code: 3, kind: NotFound })
```

**解法**：`include_bytes!` 把 77 个文件编进二进制（exe 25MB → 37MB），
`ensure_embedded_assets()` 在 `init_assets()` **之前**跑：

1. 先按上游的逻辑**从 exe 往上找** `assets/phigros.ttf` —— 找到就用，**一个字节都不写**。
   ⚠ 这一步不能省：开发时 exe 在 `target/release/`、资源在仓库根，
   少了它会被误判成「单文件分发」，把 11MB 释放进 `target/release/`，
   连带把 `data/`（谱面、配置）也搬过去 —— 那是**行为变更**，不是修 bug。
2. 往上都没有 → 释放到 exe 旁边。exe 目录不可写（Program Files 等）→ 退到系统临时目录。

⚠ 改完 `assets/` 要重跑 `huamei-tools/gen-embedded-assets.py`
（已接进 `prepare-assets.py` 的末尾）。`phira/src/assets_embedded.rs` 是**产物**，别手改。
⚠ 用 `include_bytes!` 意味着**缺任何一个资源文件都编译不过**；
`font.ttf` / `background.jpg` 是上游 gitignore 的，所以顺序必须是
**先 `prepare-assets.py` → 再 `cargo build`**。

## 8. 信任边界与反作弊（必须承认的局限）

客户端是**用户自己的机器**，所以：

- ❌ 单条成绩**不可信**。用户完全可以伪造。
- ✅ **聚合量可信**：一万条伪造数据的代价远高于刷一张谱的收益；
  且我们要的是**分布**（哪一段容易丢分），不是个人排行榜。

因此：

1. 服务端**从不下发**单条成绩作为「事实」，只用于聚合。
2. 聚合时按玩家做一次截尾（去掉每张谱最快/最慢 2% 的成绩），
   并按 `chart_digest` 分组 —— **不同 digest 的数据永不混合**。
3. 明显异常（`speed != 1.0`、`mods` 含 UNRATED、`score` 与 `counts` 对不上）
   直接拒收。这些字段客户端传了就得自洽，服务端**重算一遍**：
   `accuracy = (p + 0.65·g) / total`，`score = round((0.9·acc + 0.1·combo/total)·1e6)`。
   ⚠ 这套公式是**开源**的（`prpr/src/judge.rs:215-245`），能直接对账。

## 9. 聚合产物：「哪里失分」

按谱面 + 难度 + digest 分组，把时间轴切成 **1 秒一格**，每格统计：

```
section_stats[chart][level][digest] = {
  n_plays,                  // 有效样本数
  buckets: [                // 每格
    { t, n_notes, miss_rate, good_rate, avg_offset_ms, std_offset_ms }
  ]
}
```

站点上画成一条**沿时间轴的热力图**：越红 = 越容易丢分。
这是纯新东西 —— 现有 P.H.M. 只有「这张谱整体多难」，没有「难在第几秒」。

**样本门槛**：`n_plays < 20` 时不展示（避免一条数据就说「这里难」）。
