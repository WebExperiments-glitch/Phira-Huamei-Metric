## 一、它是什么

与 P.H.M. 定位最近的一个项目：输入谱面（官谱 / RPE / PEC / `.pez`），输出**官谱尺度**定数，
并拆成五类构成。2026-10-22 建仓，11-07 最后更新。

两个子系统：

| 模块 | 行数 | 作用 |
|---|---|---|
| `pgr2rpe/` | ~1,200 | 格式转换（官谱 ⇄ RPE、PEC → RPE），**两套独立实现互证** |
| `rating/` | ~1,700 | 特征提取、模型、校准、预测 |

`rating/features.py` 404 行，`FEATURE_VERSION = 'v12'`，产出 **111 维**特征。

## 二、完整管线（按执行顺序）

```
111 维特征（全部是玩家能理解的单位）
  ↓
HybridModel = GradientBoosting(500 树, lr 0.04, depth 3) + Ridge(alpha 8) 残差
  ↓
Calibration   单调 OOF 校准（PCHIP，范围外改用边界斜率线性延伸）
  ↓

  ↓

  ↓
TailExtrapolator 超出训练包络时向最难标签有界收敛
```

## 三、五个值得直接借鉴的设计

### 3.1 `BiasCorrection` —— 分档偏差校正

**问题**：残差曲线在 14–17 密集区可信，到 18+ 没有样本支撑，
原始残差想把 18.98 拉低 **2.9 级**。

**解法**（`model.py:204-227`）：

```python
def window(self, x):
    return np.exp(-(((x - self.center) / self.width) ** 4))   # 四次方，不是二次

def __call__(self, value):
    correction = np.clip(self.curve(x), -self.limit, self.limit)   # ±0.5
    return x - self.damping * correction * self.window(x)
```

- `center=16.2, width=1.6` —— 只在有证据的区间满强度
- **四次方**让两端衰减比普通高斯陡得多，14.5 以下、18.2 以上自然归零
- 限幅 ±0.5，防止外推失控

**为什么值得偷**：P.H.M. 目前**完全没有这一步**（`engine.js` 里 grep 不到任何 calib / 分档 / monotone）。

---

### 3.2 `TailExtrapolator` —— 有界收敛，不是线性外推

**问题**：树模型不能预测超出训练目标范围的值，比训练集最难的谱还难的谱会全部塌到同一叶子。

**但更关键的是这个实测**（`model.py:132-146` 注释）：

> 在 load score 前 8% 的 31 张谱中，**load 与难度的相关性只有 0.08**，
> 而且每一张都坐在 18.2–18.7，无论多密。
> 所以诚实的延伸不是 `load × slope`（那会给 ex8 发明出 19.8），
> 而是朝观察到的最高标签收敛。

公式：

```
y = y_max - (y_max - y_model) * exp(-k * excess)
```

单调、有界、**永不超过 y_max**。

**这直接对应我们踩过的坑**：`pred −1298 ~ +51` 那次线性外推发散。
P.H.M. 目前靠 p1~p99 裁剪护栏，那是硬夹断；这是平滑收敛，更合理。

---

### 3.3 `label_density_weights` —— 反密度加权

`model.py:59-73`：

```python
density = np.exp(-0.5 * (delta / bandwidth) ** 2).sum(axis=1)   # 标签轴上的高斯核
weight = (density / density.mean()) ** (-alpha)                 # alpha=0.5
```

注释里有一句很硬的话：

> 硬编码的「15.0–18.0 算三倍」规则没有这个性质 —— 高斯核让权重成为**标签的连续函数**，
> 所以相邻难度得到几乎相同的权重。

**意义**：解决「标签分布不均」（14–17 密、18+ 稀）时，
按区间加权会在边界产生跳变，反密度加权不会。

---

### 3.4 `HybridModel` 的残差层 —— 目的不是精度，是**连续性**

这是最容易被误读的一处（`model.py:76-105`）：

> 树集成是**分段常数**的：落在同一批叶子的谱得到**逐位相同**的预测
> （就是「为什么这么多谱都是 17.953」那个问题）。
> 加一层 Ridge 拟合树的残差，保留树的非线性，同时让输出成为特征的连续函数，
> 所以两张不同的谱总能拿到两个不同的数。

**两点**：

1. 残差层的目的是打散阶梯，不是提精度
2. 它必须裁剪到 `±2.0` —— 否则离群点（0 音符解析出 nps→1e9）会让线性项外推到 **−400**

**P.H.M. 不需要这一步**：我们是纯 Ridge，输出天然连续。
但这条提醒我们：**如果将来换 GBDT，必须同时加连续性层**。

---

### 3.5 分档报告，而不是只报总体

`model.py:315-323`：

```python
bands = [(0, 12), (12, 14), (14, 15.5), (15.5, 17), (17, 18.1)]
```

每档单独报 (n, MAE)。

**我们的做法**：报总体中位/均值/p90 + 六组切分，但没有固定难度分档。
分档能暴露「14–15 段系统性偏高」这类问题，总体指标会把它平均掉。

## 四、111 维里我们可能缺的东西

按「P.H.M. 37 维是否有对应」粗筛，以下几类**很可能缺失**：

| 特征 | 定义 | 为什么重要 |
|---|---|---|
| `throughput = nps × speed` | 吞吐量 | 同样 NPS，流速高的谱更难读 |
| `flash_load` | `exp(-fall/0.35)`，`fall = 2/speed` | 流速快→下落时间短→读谱压力（**很巧妙**） |
| `d0.25 / d0.5 / d2 / d4 / d8` | 六档时间尺度密度 | 我们可能只有 1s 一档 |
| `peak_sharpness` | `d0.5_max / d8_p90` | 瞬时爆发 vs 持续负载 |
| `rest_ratio` | 密度 < 0.5×均值 的时长占比 | 有没有喘息 |
| `density_entropy` | 密度分布熵 | 均匀 vs 忽快忽慢 |
| `trend_late_early` / `trend_slope` | 后半段/前半段、线性斜率 | 前易后难 vs 均匀 |
| `burst_count_per_min` | 超过 p90 的连续段数 | 爆发次数 |
| `hold_combo` | 按 Hold 时长加权的期间按键数 | 长条+单点复合 |
| `finale_*` | 尾杀专属（最后 25% 时长或 20s） | 尾杀 |
| `ml0.1/ml0.2` | 多判定线击打（100/200 ms 内跨线） | 多线谱 |
| `line_entropy` / `off_main_line_frac` | 判定线分布 | 散在多条线 vs 集中 |
| `type_switch_load` | tap→flick 权重 1.0、tap→drag 权重 0.05 | **drag 不吃读谱，flick 吃** |
| `hand_imbalance_p95` | 左右手负载不平衡 | 单手谱 |
| `x_jagged_*` | x 的二阶差分 = 抖动 | 来回折返 |
| `alternation` | `cross × exp(-dt/0.15)` | 轮指 |

**注意**：不是「加了就好」。我们实测 18 维扩维反而变差。
真正该试的是**逐组 A/B**，而不是整体照搬。

## 五、三条「别踩」的警告（他们踩过并写下理由）

### 5.1 jackness 跨判定线不可比

`features.py:263` 原文：

> jackness 已移除：它只比较音符的局部 x，跨判定线时坐标不可比
> （一张谱可有 58 条线），会把「不同线上的同一 x」误判成同位置连打。

**如果我们有「同位置连打 / 纵连」类特征，很可能犯同样的错。**

### 5.2 `speed_p90` 不是难度，是谱师偏好

`extrapolate.py:34-35`：

> 刻意不放 speed_p90：它是谱师的滚动速度偏好（与难度无关，
> 实测有低难谱 speed_p90 超出训练 p99 达 5 倍）

### 5.3 最难的那一端，负荷与难度几乎不相关

见 3.2 引用的实测：**前 8% 负荷的 31 张谱，相关系数 0.08**。

含义：**不要再用密度类特征去区分 18+ 的难度**。那一段的标签本身已经饱和。
这解释了为什么任何模型在高难段都难提升 —— 不是模型不行，是信号没了。

## 六、它的精度，以及为什么不能直接比

| 指标 | 数值 | 样本 |
|---|---|---|
| 官谱 5 折（按歌曲分组）MAE | **0.69** | — |
| 17+ 自制谱表留出 MAE / bias | **0.39 / −0.11** | 47 张 |
| 17–18 / 18–18.5 / 18.5+ 段 | 0.39 / 0.31 / 0.50 | 各段更少 |

**0.39 不能当作基准**：47 张、全在 17+、分布极窄。
所有谱都挤在 17~18.5 时，闭眼猜 17.75 的 MAE 也就 0.4 左右。
**这是分布宽度，不是模型精度。**

真正可比的是「官谱 5 折 MAE 0.69」。
P.H.M. 官谱留一法点误差**中位 0.500**，但口径不同（中位 vs 平均、留一 vs 5 折），
只能判断**量级相当，没有明显落后**。

## 十、核对结果：我们自己的音符口径不一致（真问题）

拆完对方的特征后，立刻回查 `phm-web/public/js/engine.js`，结论是：

**做对的部分**（`engine.js:446`）：

```js
const core=[]; for(let i=0;i<n;i++) if(types[i]===1||types[i]===2) core.push([ts[i],ticks[i]]);
```

- `types===1||2` 即 Tap + Hold，**已经排除了 drag(3/4) 与 flick**
- `real_core_notes_per_second = core.length / duration` —— 这是标准的 press NPS
- `above_avg_density_*`、`eff_peak_tps_1s` 也走 `coreT / coreK`

**做错的部分**（`engine.js:791`）：

```js
rhythmFeatures(ts),            // ← ts 是**全部音符**的时间轴
```

而 `rhythmFeatures`（`engine.js:413-423`）产出的是：

| 特征 | 含义 | 受影响方式 |
|---|---|---|
| `iv_mean` | 平均间隔 | 被 drag 拉小（间隔更短） |
| `iv_median` | 中位间隔 | 同上 |
| `chord_ratio` | < 50 ms 的间隔占比 | 被 drag 虚高 |
| `fast_ratio` | < 150 ms 的间隔占比 | 被 drag 虚高 |

**逻辑冲突**：同一份特征向量里，密度按 press 口径算、节奏按全音符口径算。
两条口径混用，而对方在 `features.py:96-106` 明确把**所有**密度/多押/手部/位移/节奏
都建立在同一条 press 时间线上：

> Drag / Flick 不吃按键，假音符已在解析阶段剔除，因此密度、多押、手部、位移、
> 节奏全部建立在同一条 press 时间线上。

### 影响面（需要实测确认，不要先下结论）

拖键/水流型谱面（drag 占比高）会被系统性影响：

- `chord_ratio` 虚高 → 可能被判定成「多押多」
- `iv_mean` 偏小 → 可能被判定成「更急促」

这两条都指向**高估 drag 密集的谱**。但这是假设，必须 A/B。

### 为什么不能直接改

`AGENTS.md` 硬约束第 3 条：**20 维特征的顺序与语义冻结，只能追加**。
直接改 `rhythmFeatures(ts)` → `rhythmFeatures(coreT)` 会让现有 Ridge 权重全部失效。

**正确做法**：

1. **追加**一组 `press_iv_mean / press_iv_median / press_chord_ratio / press_fast_ratio`
2. 单独 A/B：只加这 4 维，看 ΔR² 与配对 bootstrap CI
3. 若显著，下一个引擎版本再切换语义并重训；若不显著，保留旧口径并在注释里写明原因

这是唯一不破坏既有权重、又能验证的路子。
