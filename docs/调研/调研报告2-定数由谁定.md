## 二、Phigros 社区：唯一成体系的方法论

### 2.1 namu.wiki「难度记号问题」★ 最有价值

这是目前**最接近「社区版客观定级规范」**的东西，明确给出判定基准和分类阈值：

| 要点 | 内容 |
|---|---|
| **判定基准** | 以「**蓝V（FC）难度**」为准，而非 AP；仅「判定注意」类例外 |
| **EZ/HD 特例** | 等级记号近乎无意义，**改用物量密度**判定：密度显著高于同级→记低号，密度低→记高号 |
| 虚谱 `#F00` | EZ/HD：物量密度高于同级 3 级以上；IN/AT：难度不逊于更高级谱 |
| 水谱 `#00F` | EZ/HD：物量密度低于同级 3 级；IN/AT：不逊于低一级谱 |
| 个体差 `#92A` | 难度因玩家而异极大 |
| 配置集中 `#1A1` | 复杂配置集中于特定段落，显著影响体感 |
| 判定注意 `#F90` | AP 难度远高于 FC 难度 |
| 多色规则 | 复合谱满足 2 条以上须用 2 种以上颜色标示 |
| **社区自律要求** | 「**只记录众多用户有共鸣的案例，不写个人印象**」 |

这份文档甚至明确警告了评级反模式：

> 「不能因为同级里偏难就无条件写低号/水号。例如某曲是 7 级中下位，但比一般 6 级谱更强、或与 6 级鬼谱相当，原则上不属于水谱。」

**这是本项目最值得对标的方法论来源。**

### 2.2 社区对定数成因的共识模型

腾讯频道「Phigros音游社区」高赞长贴（作者明月星落，rks 16.37，三年内百首以上 IN 收歌、举例谱面均 99acc 以上）：

> **定数 = 客观配置难度（谱面自身，权重最大）+ 收歌难度 + 小部分大众评价**

原帖：https://pd.qq.com/s/g3sxar3hx

关键论据：

- **推分难度 ≠ 定数**：黄键多则易推分，祈 IN 上手门槛仅约 15.2 但定 16.4
- **物量影响推分**：同为 16.8，IEO AT 仅 888 物量，爆 15 个蓝 acc 即掉到 990；Solips AT 物量高则 acc 降更少
- **配置类型决定难度侧重**：BS IN 侧重底力、IEO AT 侧重协调、Avataar AT 靠段落梯度（14/15/16 → 定 16.6）
- **定数必须被大众接受**：彩与 insyde 定数互换两次来回，因「彩降下来大部分人无法接受」
- **明确承认官方无细节**：
  > 「**在官方给出定数的具体评定细节前，这个问题的讨论绝对不会停止。**」

### 2.3 锚定效应：定数不是客观难度的无偏测量 ★★

腾讯频道用户「月凝风语」[原帖](https://pd.qq.com/s/beoo3etat)：

> 「拉面馆最初定数为极其不合理的 15.3，后来经过大量玩家反馈后才勉强调到 15.5 再到定数洗牌后的 15.8，最终才到 15.9……但其定数虚低的根本原因是最初的不合理定数使得官方谱师在定数时，受到最初的『锚』的影响」

同类案例：Starduster（14.8→15.1→15.2）、小花 AT（初 14.3→现 15.4）、NO ONE YES MAN（初 15.1→现 15.5）、良怒（初 15.8→15.7→16.0）

**这条对项目是致命的**：定数不仅不等于客观难度，**它本身就不是客观难度的无偏测量** —— 它含有历史路径依赖。

**推论**：拟合目标应是**社区共识定数**，而非「真实难度」。两者会系统性偏离，且偏离方向可预测（历史定数偏低者后续上调但仍偏低）。

## 四、Phira 的事实标准：双字段一致性约束 ★★★

**这是本次调研最有工程价值的发现。**

phira.moe 前端内置了一个元数据校验器。反压缩源码：

```js
const ix = /Lv\.\s*(\d+(?:\.\d+)?)/i;
function lx(n){
  if (/^uk\b/i.test(n.level.trim())) return null;   // 占位值跳过
  const r = ix.exec(n.level);
  return r && Math.abs(parseFloat(r[1]) - n.difficulty) >= 1
    ? {key:"levelDifficultyMismatch", field:"level", level:"warning"} : null;
}
```

官方中文提示文案（原话）：

> **等级文字与难度数值不符**
> 等级文字与难度数值不一致（如 "IN Lv.14" 却对应 12.8），请修正。

**关键设计：阈值是 `>= 1` 而非 `>= 0.5` 或 `!== 0`。**

| 组合 | 是否告警 | 含义 |
|---|---|---|
| `difficulty=15.9` + `IN Lv.15` | ❌ 合法 | **「压线」惯例被官方默许** —— 15.9 表示「差一点点 16」 |
| `difficulty=15.4` + `IN Lv.15` | ❌ 合法 | 同一等级内粗粒度自评 |
| `difficulty=15.0` + `IN Lv.14` | ✅ 告警 | 跨级矛盾 |
| `difficulty=12.8` + `IN Lv.14` | ✅ 告警 | 官方举的反例 |

### 4.1 全量复现结果（我已实测跑通）

| 分区状态 | 谱数 | 触发告警 | 告警率 |
|---|---|---|---|
| **stable（已上架）** | 631 | 8 | **1.27%** |
| ranked | 587 | 8 | 1.36% |
| 未上架 | 9,058 | 299 | 3.30% |
| regular 合计 | 9,689 | 307 | 3.17% |

**这张表本身就是最有价值的数据**：已上架谱的自洽率（98.7%）显著高于未上架谱（96.7%）—— 说明这条软约束**确实在起作用**，但靠人工审核把关，不是机器强制。

对照：若用「`floor(difficulty)` 必须等于 Lv 整数」这种更严格的规则，会误报 395 张（4.85%）。官方刻意放宽到了 3.77%，**差额正是被容忍的「压线」空间**。

## 五、Phira 定数渲染逻辑（已从源码逐条核实）

### 5.1 前提：`level` 和 `difficulty` 是两个独立字段

官方文档：

> **难度** difficulty — 必需，f32，默认为 10.0 — 谱面的难度, 别乱来哈
> **难度等级** level — 必需，String，默认为 "UK Lv.10" — 显示在游玩时屏幕右下角的难度等级

编辑器源码（`prpr/src/ui/chart_info.rs:102,107`，我已本地核实）：

```rust
ui.input(tl!("level-displayed"), &mut info.level, …)              // 自由文本框
ui.slider(tl!("diff"), 0.0..20.0, 0.1, &mut info.difficulty, …)   // 0~20 滑块, 步进 0.1
```

**滑块范围 0.0–20.0、步进 0.1** —— 这是唯一存在的官方量化约束，但它约束的是**输入范围**，不是难度语义。

### 5.2 四条渲染路径（源码实证 + 已核实）

| # | 场景 | 位置 | 行为 |
|---|---|---|---|
| 1 | **游玩中 HUD** | `prpr/src/scene/game.rs:535,539`：`ui.text(&res.info.level)` | **只渲染 `level` 字符串，完全不显示 `difficulty`** |
| 2 | **选曲列表页** | `phira/src/charts_view.rs:535-537` | `level` **不含 "Lv."** 时才 `write!(" Lv.{}", info.difficulty as i32)` → **截断取整** |
| 3 | **谱面信息面板** | `phira/src/scene/song.rs:1302`：`format!("{} ({:.1})", info.level, info.difficulty)` | 两者并列，**四舍五入 1 位小数** |
| 4 | **phira.moe 网页** | 前端 JS：`${u.level} (${u.difficulty.toFixed(1)})` | 同上，1 位小数 |

**回答三个关键问题**：

- **直接显示原值还是四舍五入？** → 网页与信息面板 `{:.1}` = **四舍五入**；列表页 `as i32` = **截断**（非四舍五入）
- **整数部分（等级）怎么来的？** → **`difficulty as i32` 截断**，且**仅当 `level` 缺 "Lv." 时**才自动生成；若谱师自己写了 `"Lv.15"`，客户端**原样照抄、不做任何校验**
- **是否有 difficulty → level 换算？** → **没有**。两者是并列独立字段，唯一耦合是上述单向自动补全

### 5.3 f32 精度伪影证明「原值直传」

API 返回的 `difficulty` 带有明显 f32→f64 转换伪影：

| 谱 | level | difficulty |
|---|---|---|
| 15169 天空の城ヴェリエル | `FM Lv.17` | **17.900003** |
| 128 Ēvocator | `AT Lv.17` | **17.500006** |
| 16593 DEUX EX MĀXHINĀ | `AT Lv.18` | **18.000008** |
| 22681 Pandemic | `IN Lv.15` | **15.300005** |

**证明 difficulty 是 f32 存储、未经规范化直接透传。** 全量约 1.1%–1.6% 的谱带此类伪影。

> ⚠️ **实现要点**：解析时必须做 f32 往返归一化（`round(x*10)/10`），否则 `17.500006` 会让精确匹配失败。

> 💡 注意 15169：`FM Lv.17` 配 `17.9` —— 谱师**故意**用 17.9 表示「接近但不到 18」。这与第四节阈值 `< 1` 恰好容忍此写法完美吻合，**构成闭环证据**。

### 5.4 全量定数分布（regular 9,689 张）

**整数等级分布**：
```
Lv.14: 2036  Lv.15: 2976  Lv.16: 1754   → Lv.14–16 占 71.3%
Lv.13: 933   Lv.17: 619  Lv.12: 333
中位数 15.10
```

**小数部分分布**：
```
0.0×2940  0.5×839  0.9×789  0.2×778  0.8×777
0.4×729   0.6×722  0.7×719  0.3×675  0.1×610
→ 仅 28.6% 用整数，71.4% 用一位小数细分
```

**前缀 × 整数等级交叉表**（揭示「前缀才是真正的难度语义」）：

| 前缀 | n | 整数等级分布 |
|---|---|---|
| **IN** | 5,098 | 14×1474, **15×1936**, 16×620, 17×42 |
| **AT** | 2,017 | 15×422, **16×786**, 17×454, 18×157, 19×34 |
| FM | 99 | 14×33, 15×31, 16×11, 17×3 |
| SP | 59 | 12×1, 13×4, 14×12, 15×15, 16×9, 17×4 |

→ **前缀承担了 Phigros 难度体系（Easy/Hard/IN/AT/FM）的语义，`difficulty` 数值只做同级细分。** 一张 `IN Lv.15` 和一张 `AT Lv.15` 的 `difficulty` 字段完全相同。

**`level` 与 `difficulty` 一致性**：
- `level` 含 Lv 且 `int(difficulty) == Lv整数`：**7,798 / 8,198 = 95.12%**
- `level` **不含** "Lv"（自由文本）：1,491 / 9,689 = **15.4%**

不含 "Lv" 的自由文本实例：`IN`(271)、`AT`(98)、`IN.15`(30)、`IN 15`(19) —— **大量谱师不写 "Lv."**，依赖客户端自动补全。

## 六、Phira 上架审核：会管，但零成文

### 6.1 成文流程（官方文档一手）

| 环节 | 规则原文 |
|---|---|
| 初次审核 | 「上传或更新谱面后，谱面会进入审核队列，**需要 2 名审核员通过**方可公开」 |
| 上架申请 | 「距上次申请的冷却时间已过（**新用户至少 3 天**）。**只有谱面上传者可以发起**」 |
| 上架审核 | 「由**监督员（Supervisor）**负责，需要 **4 票通过**；若**反对票达到 3 票以上**，申请会被打回。通过后标记为 stable 和 ranked，**计入 RKS**」 |
| Stable 后限制 | 「谱面文件（`.json`/`.pec`）将被**锁定**，无法修改……**谱面名称、简介、标签等元数据仍可正常修改**」 |

> **关键**：stable 后**谱面内容锁定，但定数字段可改**（属元数据）。

### 6.2 定数合规要求：成文为零

## 七、官谱 vs 社区谱的定数差异

### 7.1 统计学差异

用「整数定数 + `level` 无 Lv 标记」作官方风格代理（n=411）：

| 群体 | n | 中位数 | 均值 | 整数定数占比 |
|---|---|---|---|---|
| **「官方风格」** | 411 | **14.00** | **13.15** | **100%** |
| 社区谱（0<diff≤20） | 9,575 | **15.10** | 14.89 | 30.4% |
| stable/ranked | 631 | 15.00 | 14.53 | 28.7% |

**三条可验证的差异**：

1. **社区谱定数系统性偏高约 1.1 级**（15.10 vs 14.00）
2. **社区谱 69.6% 用小数定数**，官方风格谱 100% 用整数 → **「整数 = 官方/传统、小数 = 社区精细化」是可观测的分界**
3. **官方风格谱分布更平缓**（8–20 级均匀），社区谱**极度集中于 14–16**（71.3%）

> ⚠️ **方法论警告**：「官方风格」代理是启发式，不是真官方谱识别（tag 仅 2 条相关，无法可靠识别）。严谨结论需下载谱包比对 `chart.json` 的 PGR 格式特征 + 音频指纹。**此项未完成。**

## 九、对项目的直接结论

### 9.1 定位必须改写

❌ 不能说：「复现 Phigros 官方定级标准」—— 它不存在
❌ 不能说：「Phigros 官方定数规则」（那条精度规则是社区观测，不是官方发布）
✅ 应当说：**「用可审计的公开规则，为 Phigros/Phira 谱面提供客观难度参考与标注合规性检查」**

### 9.2 方法论对标：namu.wiki 难度记号法

这是社区唯一写成规范的东西，五条核心原则直接可用：

1. **以 FC（蓝V）难度为基准**，而非 AP 难度
2. **EZ/HD 改用物量密度**判定，等级记号无意义
3. **显式建模五个维度**：虚谱 / 水谱 / 个体差 / 配置集中 / 判定注意
4. **只记录有共鸣的案例**，不写个人印象
5. **警惕评级反模式**：不能因为同级偏难就无条件降号

### 9.3 建模目标：拟合社区共识，而非「真实难度」

锚定效应证明：**定数本身不是客观难度的无偏测量**。所以：

- 训练/校准目标应选**社区共识定数**（Namu Wiki 定数表、B站玩家重定数表）
- 预期两者系统性偏离，且**偏离方向可预测**（历史定数偏低者后续上调但仍偏低）
- 报告中应显式声明这一点，而不是假装在测「真实难度」

### 9.4 主特征应该是「前缀 × 小数」，不是直接回归 difficulty

- 前缀（IN/AT/FM/SP）承担 Phigros 难度体系语义
- `difficulty` 只做同级细分
- 一张 `IN Lv.15` 和 `AT Lv.15` 的 difficulty 完全相同 → 直接回归会丢失难度语义

### 9.5 定数不可用玩家评分交叉验证

r = −0.07（regular 全体）。若模型算出高难度但玩家评分低，**这不是模型错误 —— 现状本就是如此**。

### 9.6 实现要点清单

| 要点 | 说明 |
|---|---|
| **f32 归一化** | `round(x*10)/10`，处理 1.1% 的伪影值 |
| **分位数截断** | 过滤 `difficulty=0`（103 张）、`>20`（plain 504 张）；troll/visual 分区均值不可用 |
| **支持十分位** | 71.4% 用小数 |
| **`as i32` 是截断** | `15.9 → Lv.15`，不是四舍五入 |
| **Liveness 校验规则** | 移植前端 `lx()`：跳过 `UK` 开头，阈值 `>= 1` |
| **15.4% 的谱不写 "Lv."** | 需从 `difficulty as i32` 补全等级 |
| **数据漂移** | 定数可被社区反馈修正（谱 22681 案例），静态数据集需定期刷新 |

### 9.7 可立即实现的高价值功能

| 功能 | 依据 | 成本 |
