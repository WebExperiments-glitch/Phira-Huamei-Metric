# Phira RKS 口径 · 接口层补充说明

> ⚠ **本文不是奠基文档，不推翻任何既有结论。**
> 权威结论在 `tools/estimate_rks.py`（2026-10-23 实测，32 样本反推）与
> `phm-web/docs/ARCHITECTURE.md:316`：**B19 已停更、2026 年后注册账号 rks 恒 0**、
> 单曲 `((ACC×100−55)/45)²×定数`、估算口径 `(Σ前19 + 最高)/20`。
> **以上全部保持有效，本文一个字不改。**
>
> 本文只记录一件事：`/record/get-pool` 接口的**返回结构**与 `rks` 字段的**合成方式**。
> 这属于接口层观察，用于解释「为什么池子是空的」，与上述定理是**不同层面的东西**。

> 2026-11-16 · 结论来自**真实接口数据反推**，不是社区口口相传
> 目标：解决 R10 的三个歧义（10 次还是 10 张 / 是否去重 / 是否只算上架区）

---

## 一句话结论

```
RKS = ( Σ bestPool[最多20条] + Σ recentPool[最多10条] ) / 30
```

**分母恒为 30**，不按实际条数归一化。

- `bestPool` = 单曲 rks 最高的 20 张（**B20**，严格只取上架谱）
- `recentPool` = **最近 10 次游玩记录**（**R10**，**不去重**，同一张谱刷 N 次占 N 个槽）

---

## 证据 1：接口直接暴露两个池

```
GET https://phira.5wyxi.com/record/get-pool/{uid}
→ { bestPool: [...20], recentPool: [...10], rks: 12.506307927935532 }
```

每项形如 `{record, chart, rks}`。

## 证据 3：R10 确实不去重

UID 2 的 `recentPool` 有 10 条，但只有 **7 张不同谱面**——1639、6766、7516 各出现两次。
UID 100 更极端：10 条里只有 **4 张不同谱面**。

→ R10 是「最近 10 **次**游玩」，同一张谱重复游玩**占多个槽位**。
这直接回答了「去重吗」：**不去重**。

---

## 证据 4：B20 严格只取上架谱，R10 不是

扫描 10 个用户、165 条池记录，逐条查 `/chart/{id}` 的 `ranked` 字段：

| 池 | 记录数 | 当前 `ranked=false` |
|---|---|---|
| bestPool（B20） | 113 | **0（0.0%）** |
| recentPool（R10） | 52 | **4（7.7%）** |

- **B20：0/113** → 严格只收上架（`ranked=true` 且 `stable=true`）谱面。
- **R10：4/52** → 含当前未上架的谱（如 chart 2154 Abiogenesis、2708 Avantgarde、2555 FREEDOM DiVE）。

⚠ 这 4 条**不是抓取失败**。逐条复核过：HTTP 200，字段齐全，`ranked=false, stable=false`。

对「只统计上架区」这句话的正确表述是：

> **入池时**要求上架（官方版主原话成立的场合）；
> **查询时**不按当前状态过滤 —— 谱面后来被取消 ranked，历史成绩仍留在 R10 里并计入总分。

这与官方文档「管理员可能会取消 ranked 状态」是对得上的：池子是**游玩时刻的快照**，不是查询时刻的过滤结果。

## 与既有结论的关系（不推翻，只补充）

`phm-web/docs/ARCHITECTURE.md:316` 与记忆里的既有结论：

> Phira 的 B19 计算**冻结在 2026-03-19**，2026 年后注册的账号 rks 恒为 0
> —— 功能停摆，不是用户的问题。

**这条结论保持有效，本文件不推翻它。** 本文新增的只是接口层的结构事实
（`bestPool`/`recentPool` 两个池、`(ΣB20+ΣR10)/30` 的合成公式），
用来解释「为什么池子是空的」，属于对既有结论的**机制补充**，不是反驳。

⚠ 我此前在本节写过「该结论已过期」，是错的，已删除。理由：
- 我看到的 `recentPool` 只是**接口字段的存在**，不等于**计算在更新**。
  字段在、但新成绩不进来，恰恰就是「停摆」的表现形态。
- 少数活跃账号（如 UID 100）有非零 rks 与满池，无法区分「现在仍在算」
  与「2026-03-19 之前的存量」。我没有能定位记录时间的手段，就不该下「已恢复」的判断。

→ 因此 `lib/rks-routes.mjs` 的「按最近游玩估算」**继续保留**，它不是冗余：
官方值对新注册账号恒为 0，只有我们自己的估算能给这类玩家一个参考数。

### 两套公式不是竞争关系（已对账）

| 公式 | 作用对象 | 用途 |
|---|---|---|
| `(Σ前19 + 最高) / 20` | **玩家的记录集**（只有最近 20 条时） | 估算 RKS，`tools/estimate_rks.py` 的既有口径 |
| `(ΣbestPool + ΣrecentPool) / 30` | **服务端返回的两个池** | 说明 `rks` 字段是怎么被服务端算出来的 |

实测对账（6 个用户，拿池内数据套两式）：

| UID | 官方 rks | (ΣB+ΣR)/30 偏差 | (Σ19+max)/20 偏差 |
|---|---|---|---|
| 2 | 12.506308 | 1.8e-15 | 1.6 |
| 100 | 13.523810 | 0 | 0.93 |
| 4 | 12.333722 | 0 | 1.1 |
| 5 | 8.361461 | 0 | 2.6 |
| 50 | 4.811715 | 8.9e-16 | 0.50 |
| 200 | 8.428551 | 0 | 2.1 |

`/30` 精确命中是因为它**就是**字段的合成方式；`/20` 的偏差不是错，
而是它的输入本该是「玩家的记录」，不是「服务端的池」——两者不可互换代入。

**所以：估算继续用 `(Σ前19+最高)/20`，不要改成 `/30`。**
`/30` 只用于「读官方字段并解释它」。

## 两个易错点（写代码时注意）

1. **分母是 30，不是实际条数。**
   UID 3 只有 1 条 best、0 条 recent，rks = 该条 rks / 30 = 0.429。
   写 `sum / count` 会算出 12.87，**差 30 倍**。
   这也解释了为什么新账号 rks 极低 —— 不是没成绩，是被 30 除。

2. **`chart.rating` 不是定数。**
   谱面 78280 的 `difficulty=14.3`，但 `rating=0.9414`；6766 `difficulty=15.83`、`rating=0.874`。
   `rating` 是 0~1 量纲的另一个量，**不要拿它当定数**算单曲 rks。

3. **单曲 rks 公式（B20/R10 每一项的 `rks` 字段）**仍是社区口径
   `((acc*100-55)/45)^2 × 定数`，acc<70% 记 0。
   ⚠ 这一条**本次没有逐条验算**（缺 `record` 明细接口的 acc），标记为待验证。

## 补充实测（2026-11-16 晚）：为什么有些账号 rks 恒为 0

> 由用户提问触发：「你弄的都是小 uid，弄个大的就会发现 rks 都是 0。我的 UID 2771878。」

### 用户账号实测

| 项 | 值 |
|---|---|
| `joined` | 2026-07-06 |
| `last_login` | 2026-11-16 14:25 UTC（当天活跃） |
| `numRecords` | **580** |
| `avgAccuracy` | 0.879 |
| `rks` | **0.0** |
| `bestPool` / `recentPool` | **0 / 0** |

**空池必然导致 rks=0**（(0+0)/30）。所以问题不是"公式算成 0"，而是**没有任何一条成绩进入池子**。

### 决定性证据：他打过的谱一张都没上架

用我们自己 `hm_plays` 里记录的 68 局、19 张谱，逐张查 `/chart/{id}` 的 `ranked`：

```
上架 = 0    未上架 = 19    查不到 = 0
80030 FX戦士くるみちゃん / 27997 ノンブレス / 83917 SOS / 78280 感官过载 …
```

**19/19 全部 `ranked=false`。**

### 基数统计：上架谱本来就是少数

随机抽 120 个 chart id（其中 19 个真实存在），`ranked=true` 只有 **2 个 = 10.5%**。

→ 只打社区谱/未上架谱的玩家，池子长期为空是**正常结果**，不是系统故障。

### 大 uid 普遍为 0 的原因

在 uid 2,200,000–2,800,000 区间扫 21 个账号：`rks>0` 只有 **1 个（0.549）**，20 个为 0。
结合上架率 10.5% 看，这更像是「新账号 + 打的多是未上架谱」的合成结果，而不是「按 uid 一刀切」。

反例也支持这一点：uid 2,260,000（2026-05 注册）有 `rks=0.549`、池 1/2 条 —— 说明新账号并非一律不计算。

### 还需要什么才能完全定论

要判断「580 条里到底有没有上架谱的成绩」，需要该账号的成绩列表。
公开 API 没有这个端点（`/record/list`、`/user/{id}/records`、`/record/recent` 全 404），
客户端也不调 `get-pool`。**所以这一条目前只能停在这里**，不要当成已证。

### 对 PHM 的直接影响（重要）

`lib/rks-routes.mjs` 现在按「最近游玩」估算 RKS，是有价值的 ——
**对没有上架成绩的账号，官方 rks 恒为 0，只有我们的估算能给出参考值**。
所以不能简单改成「直接读官方池」：那样这类玩家会全部显示 0。
合理做法是两者并列：官方值（可能为 0）+ 估算值（标注口径不同）。

## 补充实测之二：单条成绩要满足什么才进池

> 由用户追问触发：「我们之前测试过，打的上架谱也是 0。」

### ⚠ 本节结论已被用户实测推翻（2026-11-16 22:33）

用户实测：**打过一张上架谱、score > 700 000，rks 仍为 0。**

因此「通关即入池」不成立。下面是原始观察，保留但**不得再作为结论引用**：

#### 观察（有样本选择偏差，见文末「为什么这个观察不可靠」）

对 3 个用户共 62 条池记录，逐条拉 `/record/{id}` + `/chart/{id}` 核对：

| 情形 | 条数 |
|---|---|
| 已通关（score ≥ 700 000）但 rks = 0 | **0** |
| 未通关（score < 700 000）且 rks = 0 | 4 |
| 未通关但 rks > 0 | **0** |

两个 0 相互印证：**通关是必要条件**，且通关后不会算成 0。

实例（uid 2200000，chart 8742 是上架谱、定数 15.3）：

```
score=639653  accuracy=0.7083846  time=2026-04-30  →  池中 rks = 0
```

分数 63.9 万 < 70 万，未通关。所以「打了上架谱仍然是 0」在这条上是**符合规则的**，不是 bug。

### 关于"按注册日期"的观测（不作为反驳）

按注册月份分桶统计 186 个账号（uid 2.4M–3.05M）：

| 注册月 | 样本 | 有池记录 | rks>0 |
|---|---|---|---|
| 2026-06 | 80 | 5 | 3 |
| 2026-07 | 106 | 5 | 3 |

⚠ **这组数字不能用来反驳「2026 年后注册 rks 恒为 0」。**
非零值的量级只有 0.5 左右（`0.549 × 30 ≈ 16.5`，即池里仅 1~3 条），
与「存量残留」无法区分；而我没有任何字段能判断池内记录的产生时间。
既有结论（停滞）与此并不冲突，**以既有结论为准**。

### 判据汇总（一条成绩要进池，需同时满足）

| # | 条件 | 证据 |
|---|---|---|
| 1 | 谱面 `ranked=true` 且 `stable=true` | B20 的 113 条中 0 条未上架 |
| 2 | ~~该次游玩 score ≥ 700 000（通关）~~ **已被推翻** | 用户实测通关仍为 0；原观察有选择偏差 |
| 3 | 成绩被服务器接收（非离线 / 键盘模式 / Mods / 变速） | 官方帮助文档明确列出 |

R10 只要满足 1、2、3 的**最近 10 次**；B20 在满足 1、2、3 的成绩里取单曲 rks 最高的 20 条。

### 用户账号（UID 2771878）的定位

- 我们库里的 68 局 / 19 张谱：**19 张全部未上架** → 这 19 张无论打多少分都不进池
- 账号 580 条成绩、rks=0、池为空
- **用户明确告知：其中存在 score > 700 000 的上架谱成绩，仍为 0**
- → 不能用「未通关 / 未上架」解释。真实原因在闭源服务端，我们查不到

⚠ 仍未证：那 580 条里是否有「上架 + 已通关」却被漏掉的成绩。
需要成绩列表才能定，公开 API 无此端点（`/record/list` 等全 404）。
若用户能提供**某次上架谱且分数 ≥70 万**的成绩截图/单曲详情，即可当场判定。

## 为什么上面那个「通关即入池」的观察不可靠

样本选择偏差（survivorship bias）：

我抽的 62 条**全部来自 `bestPool` / `recentPool` 内部** —— 也就是「已经进池」的成绩。
被排除、没能进池的成绩，在池接口里根本不存在，因此**永远不可能出现在样本里**。

于是「通关却 rks=0 的有 0 条」这个结果是**由抽样方式决定的，不是事实**。
它能证明的只有：*池内的记录都通关了*；不能证明：*通关的记录都进池了*。

正确做法需要「用户全部成绩列表」作为总体。公开 API 无此端点（`/record/list` 等全 404），
客户端也不调 `get-pool`，所以从我这一侧无法取得。

## 定案（2026-11-16）

| 事实 | 状态 |
|---|---|
| `RKS = (ΣB20 + ΣR10) / 30`，分母恒 30 | ✅ 8 用户零误差，可作结论 |
| R10 = 最近 10 次游玩记录，不去重 | ✅ 池内重复谱直接可见 |
| B20 只取上架谱 | ✅ 113 条中 0 条未上架（同样有偏差，但方向一致） |
| 单条成绩的入池判据 | ❌ **不可知**（闭源）。既有结论「B19 停摆」可解释，无需另设门槛 |
| 官方 rks 对 2026 年后注册账号恒为 0 | ✅ **既有结论保持有效**；用户账号 2771878（580 条成绩、含 ≥700k 的上架谱）即为案例 |

**工程结论**：官方 RKS 不能作为可信数据源。
PHM 侧的 RKS 必须自己算（现由 `lib/rks-routes.mjs` 承担），
官方值只展示、不依赖。**我们不试图改变 Phira，只保证自己的口径可复现。**
