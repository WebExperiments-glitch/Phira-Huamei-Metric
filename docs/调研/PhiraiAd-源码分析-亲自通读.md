## 一句话结论

**模型不该学，特征里还有 4 个整谱统计我们没做；另外我们自己的一处 bug 修对了，被这份源码间接证实。**

## 1. 模型（`network.rs`，264 行，全部手写前向）

没有 ONNX、没有 tch。权重是 **JSON 索引 + 裸 f32 小端字节流**，加载时校验 sha256：

```rust
ensure!(meta["format"] == "phira-events-stats-f32-1" ...);
ensure!(meta["weights_sha256"] == hash(bytes) ...);
```

前向链路（我逐行读的）：

```
17 维事件 → note_encoder [17→32→32, ReLU]
  ↓ 同刻组内 mean+max 池化 → 64
  ↓ 拼 6 维组特征 → 70
group_encoder → 32
  ↓ 每 32 组一块，左右各借 4 组上下文（窗口 40）
1 层 4 头注意力（d=32, head=8, scale=√8）→ 残差 + LayerNorm + FFN
  ↓ pool(mean+max) → 64 → block_projection → 32
GRU(32) 顺序扫过所有块
  ↓
拼接 = 时长加权均值(32) + max(32) + GRU 末态(32) + 2 路注意力(各 32) = 160
  ↓ head.0 → ReLU
  + stats(18) 经 stats_projection 的残差支路
  ↓ head.3 → 标量
```

**三个设计值得注意**：

1. **同刻组而不是单音符**——和弦先按时间合并，再做 mean+max。我们的 20 维里"同按数"只是一个计数，没有组内结构。
2. **注意力分数加了时长先验**：`logits[i] += ln(duration_i)`（第 230 行）。长的段落天然权重更大，不用模型自己学。
3. **stats 走残差支路**（第 257 行），不是拼进主向量——回避了"统计量与序列特征量纲差一个数量级"的问题。

## 2. 特征（`features.rs`，449 行）

### 2.1 他们的事件级 17 维

| # | 含义 |
|---|---|
| 0-3 | 类型 one-hot（tap/hold/drag/flick） |
| 4-5 | `point[0]`, `point[1]`（判定线运动后的**屏幕坐标**） |
| 6 | `ln1p(hold 时长)` |
| 7-9 | `sin(angle)`, `cos(angle)`, `defined`（speed≠0 才有效） |
| 10 | side（±1） |
| 11-12 | `log(speed)`, `log(line_speed)`（有符号 ln1p） |
| 13-14 | `point - past`（**0.15 秒前**的屏幕位移 dx/dy） |
| 15-16 | `sin/cos(Δrotation)`（0.15 秒内的线转角） |

`angle` 的算法（第 369 行）值得抄：

```rust
angle = (rotation - 90*side + if speed<0 {180} else {0}).rem_euclid(360)
```

——把"线转角 + 上下手方向 + 速度方向"合成一个角度。侧边判定线和反速谱的朝向问题一次解决。

屏幕坐标（`Line::point`，第 168 行）：

```rust
d = x * 0.05625
[p[0] + d*cos(r),  p[1]/1.777778 + d*sin(r)]
```

`1.777778 = 16/9`，纵向做宽高比校正。`0.05625` 是他们的坐标缩放常数
（⚠ 未验证：我没查到 x 的取值域，无法确认这个常数与 675 或 1024 的对应关系）。

### 2.2 我们**没有**的整谱统计（这是最实用的部分）

他们 `stats` 18 维里，有 4 个我们完全没有：

| 统计 | 算法（`features.rs:409-440`） | 为什么我们该有 |
|---|---|---|
| **hold 覆盖率** | 所有长条占用的时间并集 / 总时长 | 我们的"当前按住数"只是逐事件快照，池化后丢了"一直有东西按着"这个性质 |
| **hold 重叠率** | 同时 ≥2 个长条的时间 / 总时长 | 双押长条是独立难度来源，逐事件计数看不出 |
| **长空档占比** | `Σ(相邻按键间隔 > 1s) / 总时长` | 我们只有 dt 分布，没有"整张谱有多少时间在休息" |
| **长条总时长占比** | `Σ(end-time) / 总时长` | 同上 |

另外他们有一个 **"按压权重"** 的概念（第 251 行）：

```rust
weight: tap=1.0, hold=1.0, flick=0.5, drag=0.0
```

drag 不占手指，权重 0；flick 只算半下。然后所有 NPS/密度类统计都用**加权**而非计数。
我们的 `1 秒窗口加权数` 是同一个思路，但权重分配未必一致——这点值得核对。

### 2.3 fake 音符：他们无条件丢弃

`features.rs:204-207`：

```rust
let fake = &n["isFake"];
if fake == &Value::Bool(true) || number(fake).is_some_and(|v| v != 0.) { continue; }
```

**我们一个都没过滤。** 演出谱（大量 fake）会被系统性高估。

## 3. ⚠ 更正上一版报告的一个错误结论

上一版写：

> 他们的 `features::extract`（raw path）和 `ai_chart_adapter`（NoteKind path）
> **kind 编号不一致**，导致 `weight()` 在两条路径上给 hold/drag/flick 相反的权重。

**这是错的。** `sanitize.rs:209-214` 在进入 `features.rs` 之前就把 RPE 原生编号重映射了：

```rust
let kind = match n["type"] {
    1 => 1,   // tap
    2 => 3,   // hold   ← RPE 的 2 是长条
    3 => 4,   // flick
    _ => 2,   // drag
};
```

重映射后与 `ai_chart_adapter.rs:156-160`（`Click=1, Drag=2, Hold=3, Flick=4`）**完全一致**。
两条路编号统一，`weight()` 是对的。上一版只读了 `features.rs` 里 `num(&n["type"])`
就直接下结论，漏了上游的 sanitize 层。

**这个更正反过来证实了我们自己的修复**：RPE 里 `2=hold, 3=flick, 4=drag`，
与我们 `chart_io.py` 改成 `{1:T, 2:H, 3:F, 4:D}` 一致。那份修复是对的。

## 4. 端侧工程（`cache.rs` / `scheduler.rs` / `index.rs`）

- `scheduler.rs` 只有 642 字节——是个很薄的封装，不是复杂的任务调度器
- `cache.rs` 用索引文件 + 分片，支持增量与失效
- 权重走 sha256 校验 + 字节偏移索引，加载时零解析开销

对我们的意义有限：我们是浏览器端、单次分析，不需要几万张谱的本地缓存。

## 5. 不值得学的

1. **它的模型**：373 张训练集 / 27,713 参数/折 × 5 折。参数:样本 ≈ 74:1。
   自报 MAE 0.52，但同谱 5 折 sd 0.54——**方差大于偏差**。
   我们 7,504 张、398 维线性模型的全谱 ρ 已经 0.832，没有学的理由。
2. **它的分块 + 上下文窗口**：32 组一块、左右各 4 组。这个设计是为了控制 O(L²) 注意力，
   本质是工程折中。我们的 patch 化（8 事件一片）出发点相同，但保留了片内全部原始值。
3. **`0.05625` 那个常数**：没搞清量纲，照抄风险大于收益（我们已有自己的屏幕坐标实现）。

## 6. 可以立刻做的三件事（按性价比）

| 优先级 | 做什么 | 成本 | 预期 |
|---|---|---|---|
| P0 | **过滤 fake 音符**，A/B | 半天 | 演出谱残差下降；零风险，随时可回退 |
| P1 | 补 4 个整谱统计：hold 覆盖 / hold 重叠 / 长空档占比 / 长条时长占比 | 半天 | 池化结构性抓不到，且与我们刚验证的 extent 不重叠 |
| P2 | 核对"按压权重"口径：drag 是否该记 0、flick 是否该记 0.5 | 2 小时 | 影响全部密度类特征 |

**不建议**：学它的架构、学它的分块注意力、抄它的坐标常数。
