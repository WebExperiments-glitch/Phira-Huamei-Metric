# 屏幕坐标特征 A/B（hit_x / anchor_dx_015 / line_speed / line_rot_speed）

> **问题**：把"移动"类特征从判定线本地坐标 `positionX` 换到判定线运动后的**屏幕坐标**，
> 到底有没有用？
> **做法**：新建 `tools/line_geometry.py`（对照仓库内 prpr 源码实现父链合成），
> 在 `build_seq_dataset.to_feats` **追加** 4 维（不改动前 20 维），用同一套切分
> 做 20 维 vs 24 维的配对 A/B。
> **数据**：`data/seq-dataset-v0.1-beta.2.npz` 的 7,504 张，现场重算特征；
> 切分 `np.random.default_rng(20261028)`、85% 训练；岭回归 α=10；bootstrap 1,000 次
> （只重采样测试集，模型固定）。
> 日期：2026-11-05。

---

## 0. 结论（先看这里）

**不值得合并。** 三条理由，从强到弱：

| # | 证据 | 数字 |
|---|---|---|
| 1 | **完整人群上没有增益** | 7,504 张：Δρ = **−0.00004**，95% CI [−0.0057, +0.0052]；ΔMAE = **+0.0008**，CI [−0.0040, +0.0052] |
| 2 | **只在 RPE 子集上有一个不显著的 ρ 提升** | 6,781 张：Δρ = **+0.0023**，CI [−0.0014, +0.0062]（含 0）。n=1018 时 ρ 的 SE≈0.031，这个差值是 **0.07 个 SE** |
| 3 | **绝大多数谱的"屏幕坐标"和本地坐标就是同一个东西** | 全语料只有 **4.9%** 的谱平均屏幕位移 > 0.05 半屏宽；中位数 **0.0037**（0.4% 半屏宽）。95% 的谱 `hit_x ≈ positionX / 675` |

唯一一个统计上站得住的收益是 **MAE −0.0048**（b 单位，CI [−0.0077, −0.0014] 不含 0，
bootstrap 胜率 99.9%），换算到定数约 **−0.005**。相对 MAE 0.427 是 **1.1%**，
低于难度标签本身的噪声量级，且要付出"JS 端全套重写 + 全量重训 + 解析耗时 +25~40%"的代价。

**建议**：不合并。若未来还要做，前置条件应该是先把"判定线运动幅度"作为语料筛选维度
（只在那 5% 上做），而不是在全体上摊薄。

## 1. 步骤 1：类型标签 —— 任务的前提是错的，我没照做

### 1.1 为什么不能"只改 `chart_io`"

任务假设「`ch` 只是中间标签，最终又转回数字，所以改标签不影响 20 维」。
**实测证伪**：`ch` 的两次映射是**反向**的，会互补抵消：

```
RPE type 3 (flick) ──chart_io──► "D" ──to_feats {D:3}──► typ 3 ──► one-hot 第 3 槽
RPE type 4 (drag)  ──chart_io──► "F" ──to_feats {F:4}──► typ 4 ──► one-hot 第 4 槽
```

只改 `chart_io` 为 `3:F/4:D` 后：type 3 → "F" → 4 → 第 4 槽，**flick 与 drag 的 one-hot
槽位互换**，同时 strain 权重从 `k∈{0,2}`（flick=1.0）变成 flick 掉进 drag 的 0.5 分支。
这不是"标签变了数字没变"，而是**数字也变了**。

所以最终改的是**两处一起**：

| 文件 | 改动 |
|---|---|
| `tools/chart_io.py` | `{1:T,2:H,3:D,4:F}` → `{1:T,2:H,3:F,4:D}`（两处：`parse_rpe`、`load_notes_ex`） |
| `tools/build_seq_dataset.py` | `{"T":1,"H":2,"D":3,"F":4}` → `{"T":1,"H":2,"F":3,"D":4}` |

### 1.2 金标对比（前后）

| 检查 | 改动前 | 改动后 |
|---|---|---|
| `cd phm-web && node tools/golden-engine.mjs` | `引擎数值金标一致 ✓` | `引擎数值金标一致 ✓` |
| `PHM_SEQ=…beta.2.npz python tools/export_engine_v3.py` | 训练 6378 · 全量 ρ(b)=**0.7987** · 权重 142 | 同左 |
| 自检 5 张谱的 b | 0.4545 / −0.9591 / −0.9368 / −0.3330 / −0.1425 | **完全相同** |
| `phm-web/public/data/engine-v3.json` md5 | `01e70edf…` | `01e70edf…`（字节级一致） |

> ⚠ `export_engine_v3.py` 默认读 `data/seq-dataset.npz`（7 维旧集）会 broadcast 报错，
> 必须 `PHM_SEQ=data/seq-dataset-v0.1-beta.2.npz`。

### 1.3 但完整数据集上**不是**零影响

| 谱型 | 张数 | 与 beta.2 数据集的最大差异 |
|---|---|---|
| RPE | 6,781 | 连续量 **≤0.078**（float16 量化）；另有 3 张的 ±20ms/±250ms **计数**差 1–2（最大池化差 2.0，来自 8,000 事件截断处的排序 tie） |
| PEC（扩展名 .json、内容是 PEC） | 723 | **1.0**，其中 573 张：第 6/7 列 one-hot 互换；其余 150 张无 flick/drag，完全不变 |

PEC 谱的 `parse_pec` 把 n3 标成 "D"、n4 标成 "F"，历史口径把 drag 放进了 F 槽；
标签修正后它回到 D 槽 —— 这是**修对了**，但与已训练权重不一致：

| 20 维特征来源（同一生产切分，n_train 6368 / n_test 1124） | ρ_test | MAE |
|---|---|---|
| beta.2 原特征（legacy） | 0.8028 | 0.4413 |
| 现场重算（修正后） | **0.7997** | 0.4441 |

**代价 −0.0031 ρ。** 这不在本次任务范围内，需要 team-lead 定：
要么接受并在下次重训时一并消化，要么把 `to_feats` 的两列语义修正回滚（保留 `chart_io` 的标签修正）。

### 1.4 顺手修掉的两个真 bug（与标签无关，但影响面更大）

1. **`load_notes_ex` 的 PEC 分支漏了排序**。`parse_pec` 按文件行序返回（按判定线交错），
   而 RPE 分支末尾有 `out.sort`。结果 723 张 PEC 谱的 dt 出现负值（被 clamp 成 0）、
   ±250ms 密度窗和 strain 全部算在乱序时间轴上。
   证据：1027 号谱 Σdt = **987.0s**（错），排序后 = **215.5s**（与 beta.2 一致）。
   已修（`chart_io.py` PEC 分支加排序）。
2. **`_line_tracks` 不跳过 `eventLayers` 里的 `null`**。prpr 的结构是
   `Vec<Option<RPEEventLayer>>`，真实语料里有 null 图层；不跳过会让 12 张谱
   （含最大两张 16MB / 23MB）整张抛 `AttributeError` 被丢弃。已修。

另外把 `_track_value`（每次查询都从头 `_frac` 整条轨道）改成预解析 + 二分：
单张 2,260 音符的谱 **33 s → 0.29 s**（`20,351,400` 次函数调用里 `_frac` 占 4.4M 次）。
这跟功能无关，但全量跑得动全靠它。
⚠ 副作用：事件交界处若下一段的 `start` 与上一段的 `end` 不等（跳变），
旧实现对**恰好等于交界拍**的音符取上一段的值，新实现取下一段的 `start`（与 prpr 的
keyframe 语义一致）。只影响第 23 列 `|Δsx|`（sx 派生），**不在 20 维模型里**。

## 2. 步骤 2：`tools/line_geometry.py`

### 2.1 实现依据（不是猜的）

直接对照仓库里的 prpr 源码：

- `phira-huamei/prpr/src/core/line.rs::JudgeLine::{fetch_rot, fetch_pos, now_transform}`
- `phira-huamei/prpr/src/parse/rpe.rs`（坐标缩放因子 `2/RPE_WIDTH`、`2/RPE_HEIGHT`、
  旋转 `factor = -1`）

```
rot(i, t) = -Σ_layers rotateEvents(i, t) + (rotateWithFather ? rot(parent, t) : 0)
pos(i, t) = pos(parent, t) + R(rot(parent, t)) · own(i, t)      # 位置总是继承父级旋转
own(i, t) = ( Σ moveXEvents / 675,  Σ moveYEvents / 450 / (16/9) )
note      = pos(i, t) + R(rot(i, t)) · (positionX / 675, note_y)
```

对外接口（内部一律归一化屏幕坐标，出口乘回 675，与 `positionX` 同尺度）：

```python
screen_x(line, beat, local_x, parent_rot_deg=0.0, parent_pos=(0,0))  # 单层
ChartGeometry.screen_xy(line_idx, beat, local_x)                    # 含父链
ChartGeometry.line_speed(line_idx, beat, bps)   # RPE 屏幕单位/秒
ChartGeometry.rot_speed(line_idx, beat, bps)    # 度/秒（绝对）
```

### 2.2 与任务描述的三处出入（都以实测为准）

1. **父链不是 `judgeLineGroup` 字符串**。真实字段是 `father: int`（指向
   `judgeLineList` 下标，`-1` 为无父级）；`Group` 只是分组号。按字符串匹配会得到 0 条父链。
   实测前 225 张：503/约 6,000 条线有父级 → 必须实现。
2. **`rotateWithFather` 在语料里从未出现**（前 3,590 条线 0 次）。所以"父级旋转继承"
   实际不生效；但"父级位置继承 + 父级旋转作用于子级平移"是生效的，已实现。
3. **旋转符号是负的**（prpr `factor = -1`）。对 x 无影响（cos 偶函数），只影响 y 分量，
   已按 prpr 处理。

### 2.3 自测输出（`python tools/line_geometry.py`）

```
line_geometry 自测
  [OK ] 静止                     expect= 300.000 got=  300.000000 err=0.00e+00
  [OK ] 纯平移                    expect= 135.000 got=  135.000000 err=0.00e+00
  [OK ] 旋转90°                  expect=   0.000 got=    0.000000 err=6.12e-15
  [OK ] 父链(父转90°子平移100)         expect= 200.000 got=  200.000000 err=0.00e+00
  [OK ] 旋转90°的y分量              expect=-100.000 got= -100.000000 err=0.00e+00
全部通过（容差 1e-6）
```

用例是手算可验的：静止 → `screen_x = local_x`；moveX 0→270 每 8 拍、第 4 拍 → 135；
rot 90°、local_x=100 → x=0、y=−100；父 moveX=200 + 父转 90° + 子 moveX=100 → 子世界 x=200。

### 2.4 明确标注的近似

| 近似 | 说明 |
|---|---|
| 缓动 | **只做线性插值**，忽略 `easingType`。与 `chart_io._track_value` 同口径；`start==end` 的保持型事件精确 |
| 多 eventLayers | 按 prpr `AnimFloat::chain` 的**求和**语义（`a1+a2+…`）；单图层时与旧实现等价 |
| 首事件之前 | 取首值（prpr 实际线性外推）；语料事件几乎都从 0 拍起 |
| 忽略 | `height`/`speedEvents` 的 y 积分、`skew`、`size`、音符 yOffset |
| 不可解析 | 父链成环 / `father` 越界 → 抛异常并计数，不静默修补 |

## 3. 步骤 3：特征与 A/B

### 3.1 追加的 4 维（`to_feats` 第 24–27 列，前 24 列原样不动）

| 列 | 名称 | 定义 | 单位/裁剪 |
|---|---|---|---|
| 24 | `hit_x` | `screen_x / 675`（含父链） | 半屏宽，裁 ±4 |
| 25 | `anchor_dx_015` | 当前音符与 `[t−0.15s, t)` 那批音符**平均**屏幕 x 之差 / 675 | 裁 ±8 |
| 26 | `line_speed` | 判定线位移速度 / 675（**每秒**，不是任务里写的"每分钟"） | 半屏宽/秒，裁 200 |
| 27 | `line_rot_speed` | 判定线角速度绝对值；角度差按 ±180° 归一避免 360→0 假跳变 | 度/秒，裁 36000 |

> `anchor_dx_015` 按**任务给的定义**（与上一批音符比），不是 PhiraiAd 的
> "同一音符 t 与 t−0.15 的位置差"（纯判定线位移）。两者口径不同，已在代码注释里写明。
> 裁剪只为挡住"判定线飞出屏幕（moveX=100000）"的极端样本：`hit_x` 裁 ±4 只影响
> <0.1% 的事件，`line_speed` 裁 200 只有 0.3% 事件命中。

分布（RPE 6,781 张）：

| 量 | p50 | p90 | p99 | 零值比例 |
|---|---|---|---|---|
| max `line_speed`（半屏宽/秒） | 37.5 | 145.7 | 200（裁满） | 1.8% |
| max `line_rot_speed`（度/秒） | 742 | 9,000 | — | 3.0% |
| `|mean(hit_x) − mean(x)|` | 0.0037 | 0.027 | 0.161 | — |

**这里是最关键的一行**：中位数谱的屏幕位移只有 **0.4% 半屏宽**，
只有 **4.9%** 的谱超过 5% 半屏宽。RPE 谱的判定线绝大多数时候是"站在中间不动"的。

### 3.2 主分析：RPE 子集 6,781 张（新特征有定义的人群）

训练 5,763 / 测试 1,018；同一 `permutation(seed=20261028)`；α=10。

| 指标 | 20 维 | 24 维 | 差值 Δ | 95% CI（bootstrap 1,000） | bootstrap 胜率 |
|---|---|---|---|---|---|
| ρ（b） | 0.7981 | 0.8004 | **+0.0023** | [−0.0014, +0.0062] | 87.7% |
| MAE | 0.42704 | 0.42228 | **−0.0048** | [−0.0077, −0.0014] | 99.9% |

参考噪声标尺：n=1018 时 ρ 的 SE ≈ **0.031**，Δρ 只有 **0.07 SE**。
把 28 个新池化维**整体按谱打乱**（破坏对应关系）的对照：Δρ = **−0.0010**。
即"加 28 维本身"带来的波动就有 0.001 量级，真特征的 +0.0023 没有明显跳出这个地板。

### 3.3 次分析：全部 7,504 张（含 723 张 PEC，其 4 个新维恒为 0）

训练 6,378 / 测试 1,126。

| 指标 | 20 维 | 24 维 | Δ | 95% CI |
|---|---|---|---|---|
| ρ | 0.79952 | 0.79949 | **−0.00004** | [−0.0057, +0.0052] |
| MAE | 0.44417 | 0.44492 | **+0.0008** | [−0.0040, +0.0052] |

PEC 谱的 28 个新维是常数 0，等于给模型塞了一批"是不是 PEC"的哑变量，
把 RPE 子集上那点收益完全摊平 —— 这本身也说明收益不稳。

### 3.4 单特征消融（RPE 子集，每次只加 1 个新维 = 7 个池化量）

| 特征 | ρ | Δρ | MAE | ΔMAE |
|---|---|---|---|---|
| `hit_x` | 0.80058 | **+0.00248** | 0.42381 | **−0.00323** |
| `anchor_dx_015` | 0.79713 | −0.00098 | 0.42842 | +0.00138 |
| `line_speed` | 0.79857 | +0.00046 | 0.42582 | −0.00122 |
| `line_rot_speed` | 0.79793 | −0.00017 | 0.42758 | +0.00053 |

**全部收益来自 `hit_x` 一个特征**，另外 3 个单独加基本是 0 或负。
这跟分布对得上：`line_rot_speed` 在 3% 的谱上是 0、p50 已到 742 deg/s、p90 裁满，

### 3.5 子组

| 子组 | n（测试集） | ρ20 | ρ24 | Δρ |
|---|---|---|---|---|
| max line_speed 高于中位 | 509 | 0.7986 | 0.8006 | +0.0020 |

## 4. 该不该合并：不该

1. **效应量低于噪声地板。** 完整人群 Δρ = −0.00004；RPE 子集 +0.0023（0.07 SE）。
   报告要求"0.03 以内是噪声"，这里连 0.003 都没到。
2. **收益来源单一且可被现有特征替代。** 只有 `hit_x` 有一点信号，另外 3 维为 0；
   而 `hit_x` 与现役第 2 列 `x/675` 的相关是 **0.62**，本质是同一个量加了一点线偏移。
3. **前提只对 5% 的谱成立。** 中位谱的屏幕位移 0.4% 半屏宽。要做这件事，正确的前置
   是先把"线运动幅度"做成语料筛选/分层，在 5% 的子群上单独建模或加交互项，
   而不是在全体上追加 4 个近似共线的维。
4. **工程代价不低。** 解析耗时 +24~38%；上线要 Python + JS 双端一致（`line_geometry`
   的父链、旋转符号、`eventLayers` 求和语义都要在 `engine-v3.mjs` 重写一遍并对拍），
   而 v3 的 142 权重必须重训。

**如果一定要留一点东西**：`hit_x` 单独加（+0.0025 ρ / −0.0032 MAE），
并同时修掉 1.3 的 PEC one-hot 口径。但仍然不建议现在动线上权重。

## 6. 未做 / 已知限制

- **PEC 判定线几何未实现**：PEC 的 `cm`/`cr` 行没解析，723 张 PEC 谱的 4 个新维恒为 0。
  这是次分析被摊平的直接原因，也是"完整人群无增益"的一部分。要做全，需要补 PEC 的
  判定线轨道解析（工作量约同 RPE）。
- **缓动仍为线性**：所有 `easingType` 视为线性。对 `start==end` 的保持型事件精确，
  对曲线缓动有偏差；这会影响 `line_speed`/`line_rot_speed` 的瞬时值（不影响 `hit_x` 的
  端点值）。
- **`anchor_dx_015` 用了任务口径**（与上一批音符比），没做 PhiraiAd 的"同一音符回看
  0.15s"版本。后者更接近"读谱提前量"，值得单独试一次 —— 但按这次的结果，预期同样很小。
- **没做按谱师/时间的分组切分**：本次只用了随机切分（与线上 v3 同口径），
  目的是可比，不是泛化性审计。
- **没重训线上权重、没改 JS**：本次只到"值不值得"的判定为止。
