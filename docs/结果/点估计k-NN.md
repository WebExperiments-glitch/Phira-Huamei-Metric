# 点估计：k-NN（现行方法）

> 2026-10-05 · 取代 v2「分层查表」
> 一键复现：`python tools/exp_point_estimate.py`（方法选型）、
> `python tools/pipeline.py calibrate`（精度 + 前后端一致性）

---

## 一、为什么改：用户要的是数字，不是区间

产品反馈：「用户其实想要的是精确的数值吧。我们不能只给个大概。」

但**精确数值不能凭空给** —— 官谱定数本身是人工标注，实测噪声 **2.80 级**。
直接报「15.32」会制造虚假精度。

**解法不是放弃区间，而是把点估计推到前面、把不确定度如实标在旁边：**

```
       15.5   ± 1.0
       ↑ 主答案      ↑ 实测误差（约 2/3 的谱在此范围内）
```

既然要给一个数，就必须让这个数尽量准。于是做了方法选型。

## 二、方法选型（留一法，官谱 1,037 条）

| 估计器 | 中位误差 | p75 | p90 | ≤0.5 | ≤1.0 |
|---|---|---|---|---|---|
| 查表（难度标签 × NPS档 × Hold档） | 0.600 | 1.050 | 1.500 | 46.1% | 74.5% |
| k-NN k=5 | 0.600 | 1.100 | 1.700 | 46.3% | 74.5% |
| k-NN k=10 | 0.500 | 1.000 | 1.500 | 51.5% | 78.4% |
| **k-NN k=20（采纳）** | **0.500** | **1.000** | **1.500** | **56.2%** | **80.7%** |
| k-NN k=40 | 0.500 | 1.000 | 1.500 | 55.4% | 80.3% |
| k-NN k=20，全标签混池 | 0.800 | 1.500 | 2.400 | 41.2% | 67.4% |

**三条结论：**

1. **k-NN 优于查表**：中位误差 0.600 → 0.500，≤1.0 命中 74.5% → 80.7%。
2. **必须按难度标签分层**：全标签混池会把误差抬到 0.800（−60% 命中率）。
   物理原因：EZ 与 IN 的谱面特征有重叠区，但定价基线差 10 级。
3. **k=20 是拐点**：k=10 与 k=20 中位相同，但 k=20 的 ≤0.5 命中高 4.7 个百分点。

### 特征集也要选，不拍脑袋

| 特征集 | 是否 z-score | 中位误差 | ≤1.0 |
|---|---|---|---|
| NPS + 长条占比 | raw | 0.600 | 75.1% |
| NPS + 长条占比 | z-score | 0.500 | 77.4% |
| + 物量 | z-score | 0.500 | 79.6% |
| **+ 纵连速度（采纳）** | z-score | **0.500** | **80.7%** |

**「纵连速度」加进来有效，这件事本身值得记一笔。**
同一个维度，早前作为**离散分档**加进查表时会让精度**变差**
（0.700 → 0.800，见 [18维要素实验结果](18维要素实验结果.md)），
原因是被摊薄成每格十几条样本；而作为**连续距离**的一维，它是有用信号
（控制 NPS 后偏相关 +0.52，全项目最强残余信号）。

→ 教训：**「加维度没用」和「用连续距离没用」是两回事**，
不能因为前者失败就否定后者。

## 三、现行算法（唯一真源 `phm/core.py`）

```
特征   X = [log1p(NPS), log1p(长条占比%), log1p(物量), log1p(纵连速度)]
        （四个特征各自 z-score）

检索   在【同难度标签】的官谱内，按标准化欧氏距离取最近 20 首
       （标签内不足 20 首时放开到全体 —— 小标签 AT 仅 56 条）

预测   加权分位：权重 w = exp(−(d/d_max)² × 2)
       点估计 = 加权 P50；不确定带 = 加权 P25 ~ P75
```

**为什么这样可审计**：点估计就是「这 20 首官谱定价的中位」，
每一首都能列出来查证（界面上的「官谱参照」用的就是同一批近邻 —— 一次计算，两处使用）。

## 四、精度（交付引擎实测）

```bash
python tools/pipeline.py calibrate
```

| 指标 | 值 |
|---|---|
| 点误差 中位 | **0.500** |
| p75 / p90 / p95 | 1.000 / 1.500 / 1.900 |
| ≤0.5 / ≤1.0 / ≤1.5 | **55.5%** / **80.8%** / 93.2% |
| 近邻集中度（high/mid/low） | 563 / 446 / 28 |
| 不确定带覆盖率 | **55.4%** |

**区间覆盖率 55.4% 的含义**：把规则套回官谱自己，
**44.6% 的官谱落在自己的同类区间之外**。
→ 所以「偏离点估计」不构成标注错误的证据。

> 置信档含义：近邻定价越集中（P75−P25 越小），说明该谱型在官谱里有共识，
> 估计越可信。high ≤1.0 / mid ≤2.0 / low >2.0。

## 五、前后端一致性（浏览器端是独立实现）

GUI 没有 Python 运行时，k-NN 只能复制一份 JS。复制就会漂移，故有两道防线：

1. **构建期** `check_gui_core_parity()`：校验 `KNN_K`/`KNN_BW` 参数、
   并在 node 里跑 GUI 的 `knnFeats` 与 `core.knn_feats` **逐值比对**
   （测试样本覆盖 `max()` 守卫的边界，否则公式改了也测不出来）。
2. **逐谱比对** `tools/verify_gui_parity.py`：抽取 GUI 的 k-NN 函数，
   对真实官谱语料跑，与引擎比对 point / lo / hi。

**这两道防线已各抓到一次真问题**：
- 断言最初只用了物量 ≥2 的样本，`log1p(max(notes,1))→log1p(max(notes,2))` 的漂移被放过
- 逐谱比对抓到：GUI 的 query 长条占比漏了 `×100`，
  导致 query 向量与语料向量不在同一尺度、近邻全错（65/65 全部不一致）

## 六、与旧方法的关系

| | 旧：分层查表（v2） | 新：k-NN（v3，现行） |
|---|---|---|
| 形式 | 离散分档，查表取中位 | 连续距离，加权分位 |
| 中位误差 | 0.600 | **0.500** |
| ≤1.0 命中 | 74.5% | **80.8%** |
| 可解释性 | 每格可追溯到样本 | 近邻可逐首列出 |
| 弱信号利用 | 分档摊薄样本 → 用不上 | 连续距离 → 用得上（纵连） |

查表法的完整记录见 [定数公式v2（历史）](定数公式v2.md) —— 保留作为精度对比基线。
