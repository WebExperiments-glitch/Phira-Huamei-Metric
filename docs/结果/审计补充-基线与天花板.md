# 审计补充：基线、天花板与时间外推

> 一次性复现：`node phm-web/tools/audit-baselines.mjs`（约 20 秒，无需联网、无需数据库）
> 语料快照：2026-10-20（社区参照集 9,508 张生产行 / 官谱 1,037 张）
> 状态：**已并入 `tools/pipeline.py calibrate`**，改引擎或改参照集后必跑

---

## 为什么要做这份审计

已有文档回答了「我们的引擎比旧引擎好多少」，但没回答三个更要紧的问题：

| 问题 | 为什么必须回答 |
|---|---|
| ① 比**最笨的基线**好多少？ | 只报「比 4 维 k-NN 好」是不够的 —— 任何预测器都打败「猜一个常数」。读者真正想看的是差多少。 |
| ② 这 8 维结构**最多能解释多少**？ | 命中率 84% 不等于「难度算得准」—— 真值本身就是人工声明值，它含噪声，也含别的东西。 |
| ③ 换成**更新的谱**还准吗？ | 随机留出与调参集同源，天然偏乐观。这个偏差有多大，没人量过。 |

这三个问题都能用现有数据回答，一个下午就能跑完。**跑不出来就等于没有。**

---

## 方法纪律

- k-NN 那一行走的是**引擎真正的那条路径**（`public/js/engine.js` 的 `knnReference`），
  不是重写的一份 —— 重写就跟线上不是同一个算法了，验证就成了假的。
- 参照集用 `buildCommunityRows()`（生产行，与线上同源），不自己写过滤逻辑。
- 指标口径与 `tools/validate-ref.mjs` 完全一致：`|偏差|` 中位 / 均值 / p90、≤1.0、≤1.5、R²。
- 基线是**故意做笨的**：常数中位数 / 8 维线性回归 / 单特征 1-NN。
  它们不是稻草人 —— 8 维 OLS 是任何认真做「结构→定数」的人都会先跑一遍的东西。

## ① 相对基线

同一留出集（随机留出 1,394 张，参照 8,114 张），真值 = Phira 声明定数：

| 方案 | \|偏差\|中位 | \|偏差\|均值 | p90 | ≤1.0 命中 | ≤1.5 命中 |
|---|---|---|---|---|---|
| **k-NN（现行引擎）** | **0.443** | 0.827 | 1.42 | **81.7%** | 91.0% |
| 8 维线性回归（OLS） | 0.519 | 0.892 | 1.55 | 78.3% | 89.5% |
| 单特征 NPS 1-NN | 0.800 | 1.438 | 3.00 | 59.4% | 74.0% |
| 常数中位数 | 0.900 | 1.388 | 2.90 | 52.4% | 69.4% |

**读法**：k-NN 比「同样这 8 个特征的线性回归」好 **3.4pp**（≤1.0 命中）、中位误差小 0.076，
比「猜常数」好 29pp。

> ⚠ 此前文档里唯一的「拟合公式」对照是 **26 维岭回归 1.042** ——
> 那是一个被特意配弱的对手，撑不起「查表比拟合公式更合适」这句话。
> 换成同样特征的朴素 OLS 之后，正确的结论是：
> **局部近邻确实更好，但优势没有大到可以忽略模型形式。**

## ② 天花板：结构能解释多少，剩下的归谁

| 量 | 值 | 含义 |
|---|---|---|
| R² | **0.382** | 这 8 维结构只解释了声明定数 **38%** 的方差 |
| 残差里「谱师间」可解释 | **60.8%** | 模型算不准的部分，大头是**这个谱师习惯标高还是标低** |
| 同上（id 分块留出，样本更大） | **55.6%**（112 个谱师 / 415 张谱） | 结论不随样本量翻倍而变 |

**推论（已写进 README 首屏）**：

1. 声明定数 = 结构 + 谱师习惯 + 说不清的那部分。**只看谱面的工具拆不开后两块。**
2. 「谱师习惯」是**系统性偏移**（这个人整体标高或标低），不是随机抖动 ——
   所以它**不该靠放宽不确定带来解决**，而该进点估计的修正项
   （按谱师建模，见后续动作）。**这点很重要：带不是越小越诚实，也不是越宽越诚实。**
3. 网页版现有不确定带（20 个近邻的 min/max）实测覆盖率 **90.9%**，
   **可以直接当区间读** —— 不需要为了「装下谱师习惯」去加宽它。

> ⚠ 这一项是**分组方差占比**，不是严格意义的 ICC。
> 「谱师间可解释」里混着谱师的**选曲偏好**（他常写什么档位），
> 未必全是「标定偏差」。要拆干净需要更大样本 + 谱师作品分层统计，暂列为待办。

## ③ 时间外推：换更新的谱还准吗

Phira 的 chart id 随上传顺序递增，所以「id 分块」可以模拟
「参照集是老的、预测的是后来才上传的谱」—— 这是时间外推的**保守下界**。

| 切分 | 参照 / 测试 | \|偏差\|中位 | \|偏差\|均值 | p90 | ≤1.0 命中 |
|---|---|---|---|---|---|
| 随机留出（项目口径） | 8,114 / 1,394 | 0.443 | 0.827 | 1.42 | 81.7% |
| **id 分块留出** | 4,755 / 3,000 | **0.573** | 0.961 | 1.71 | **75.0%** |

**差 6.7pp。** 这 6.7pp 里混着两件事，暂时无法分离：
（a）时间外推本身的难度增加；（b）超参（8 维 / k=20 / 带宽 2.0 / 15% 截尾）
是在同一批语料上选的。

### 更接近真的：按**上传时间**切

id 只是「更晚注册」，`created` 才是**上传时刻**。
`tools/fetch_chart_list.py` 拉 Phira 公开列表（`order=-created` 倒序），
把每张谱的 `created` 落成 `data/chart-list.jsonl`（**不入库**，可随时重拉），
审计工具就能按真实上传时间切：

```bash
python tools/fetch_chart_list.py            # 拉列表（带 created）
node phm-web/tools/audit-baselines.mjs --split created
```

切法：分界日 D 取上传时间的中位数，参照 = `created < D`，测试 = `created ≥ D`；
没有上传时间的行**不进测试集**（时间未知，混进去会把「时间外推」变成「说不清」）。

**实测**（语料 2026-10-20，分界日 2025-03-11，参照 4,731 / 测试 3,000）：

| 切分 | \|偏差\|中位 | \|偏差\|均值 | p90 | ≤1.0 命中 | 带覆盖率 |
|---|---|---|---|---|---|
| 随机留出（项目口径） | 0.443 | 0.827 | 1.42 | 81.7% | 90.9% |
| id 分块留出（代理） | 0.573 | 0.961 | 1.71 | 75.0% | 87.0% |
| **created 切分（真上传时间）** | **0.581** | 0.990 | 1.74 | **74.6%** | **86.7%** |

**这一行是本次审计最有用的一条**：id 分块是「用 id 当上传时间的代理」，
而 created 切分是**真的上传时间**。两者结果几乎重合（0.573 vs 0.581、
75.0% vs 74.6%）⇒ **id 代理是可信的**，以后想快速估时间外推的代价，
用 id 分块就行，不必每次都拉列表。

同时它也再次确认：随机留出的 81.7% 是**乐观**的，
时间外推下的真实水平是 **~75%**（≤1.0 命中），差约 7pp。

**再往后要真正的 future holdout，只有增量抓取一条路**：
`fetch_chart_list.py --since <日期> --merge` 可以只拉新上传的谱并合并进
`data/chart-list.jsonl`，攒够一批后单独评。

## ④ 附：把「官方标注噪声 2.80」拆开看

旧文档把「同曲 + 物量相近（±15%）的**相邻难度**定数差中位 = 2.80」称为
「官方标注噪声」，并据此说「没有任何工具能区分谱师标错与官方也会这么标」。

按档位对拆开后：

| 档位对 | n | 定数差中位 | p90 |
|---|---|---|---|
| EZ→HD | 8 | **4.60** | 4.90 |
| HD→IN | 24 | **3.50** | 4.90 |
| IN→AT | 24 | **1.10** | 1.80 |
| 合计 | 56 | 2.60 | — |

**读法**：这个中位几乎全部由 EZ→HD、HD→IN 贡献 —— 那是**档位的设计差异**
（同一首歌的 EZ 和 IN 本来就该差好几级），不是「同一难度上重复标注的抖动」。
把它当噪声地板，会被本工具自己的实测（误差中位 0.44）反证。

**结论要保留**（不判定虚标），但**支点要换**：

- 旧支点：「官方噪声 2.80 → 谁也做不到」→ 站不住。
- 新支点：「结构只解释 38%，残差里 60% 是谱师习惯 → 只看谱面的工具本来就不该下判决」→ 站得住。

## ⑤ 不确定带：这个带能不能当区间读

两套引擎的带**语义不同**，必须分开看：

| 引擎 | 带的定义 | 实测覆盖率 | 半宽中位 |
|---|---|---|---|
| 网页版（`engine.js`） | 20 个近邻定数的 **min/max** | **90.9%** | **±1.50 级** |
| 桌面 / CLI（`phm/core.py`） | 近邻定数的**加权 P25/P75**（四分位距） | 55.4% | — |

**网页版的带可以直接当区间读。** 桌面引擎那个**不行**：
四分位距按定义只盖住一半质量，55.4% 是它的数学后果，
把它当置信区间读，就会得出「连官谱自己都对不齐」的错误结论。

> ⚠ 旧版 README 首屏写过「44.6% 的官谱落在自己的同类区间之外 → 官方乱标」。
> 那条推断建立在「55.4% 是异常」这个前提上，而前提本身是四分位距的数学性质。
> **这条推断作废。**
>
> 本次已给桌面引擎补上同口径的全跨度带（`Verdict.full_span_band()`），
> 官谱留一法实测覆盖率 **92.8%**（半宽中位 ±1.75 级），
> 与网页版的 90.9% 一致 —— 两套引擎现在可以直接比较了。

### 候选带定义（网页版，随机留出 1,394 张）

| 带定义 | 覆盖率 | 半宽中位 |
|---|---|---|
| 近邻 min/max（**现行**） | **90.9%** | ±1.50 级 |
| 近邻 q10–q90 | 77.9% | ±0.80 级 |
| ref ± 1.0·σ_n | 73.1% | ±0.74 级 |
| ref ± 1.5·σ_n | 86.0% | ±1.11 级 |
| ref ± 2.0·σ_n | 91.8% | ±1.48 级 |
| **ref ± 1.78·σ_n**（解到 90% 覆盖） | 90.0% | ±1.32 级 |
| **ref ± (1.0·σ_n + 0.51)**（固定项 = 结构之外那部分） | 90.0% | ±1.25 级 |

**读法**：

- 想让带**看起来更准**（比如收窄到 ±1.0 以内），代价是覆盖率掉到 73% 以下 ——
  也就是**近三成的谱会落在带外**。当前 ±1.50 是有实测支撑的。
- 固定项 0.51 级是「结构解释不了的那部分」的成本（谱师习惯等）。
  换句话说：**带里真正装下谱师风格的版本，宽度和现在差不了多少。**
  这与「残差里 60% 是谱师间方差」并不矛盾 —— 谱师风格是**系统性偏移**
  （同一个人整体标高或标低），不是**随机噪声**，它不该放大带子，
  而该进点估计的修正项（那需要按谱师建模，属于下一步的活）。

### ⚠ 这份审计**没有**回答的问题（别过度解读）

- 它**不能**说明哪个定数是对的。它只说明「预测声明值」这件事的天花板在哪。
- id 分块是时间外推的**代理**；按 created 切更准，但仍不是真 future holdout
  （测试集里的谱在语料快照时就已存在）。
- 谱师内聚用的是**分组方差占比**，样本量在随机留出下偏小（22 个谱师 / 77 张谱），
  结论以 id 分块那次（112 / 415）为准。
- 所有数字都依赖 `data/community.jsonl` 这一份快照。语料更新后必须重跑。
