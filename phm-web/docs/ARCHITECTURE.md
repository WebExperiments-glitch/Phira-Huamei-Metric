## 站点结构（2026-10-07 起是多页，不再是一个 index.html）

| 路径 | 文件 | 干什么 |
|---|---|---|
| `/` | `index.html` | 落地页：这是什么、双标度怎么读、三个入口、实时统计 |
| `/app` | `app.html` | 分析工作台：拖入谱面包 / 搜谱面 / 出定数 / 导出分享卡 |
| `/charter` | `charter.html` | 谱师页：某个谱师的全部作品、档位分布、每张谱的 P.H.M. 定数 |
| `/user` | `user.html` | 玩家页：成绩、自算 RKS、最近游玩、任意单谱的全部成绩 |
| `/data` | `data.html` | **数据管理**：全库分页浏览、排序、过滤；每行的双标度与引擎版本 |
| `/settings` | `settings.html` | **设置**：上传偏好 / Phira 连接信息 / 本机存储清单与清除 / 关于 |
| `/en.html` | `en.html` | 英文落地页（给 X 上的国际用户） |

**为什么拆**：①面板方案下链接没法指向"某人的成绩 / 某谱师的作品"，
而分享链接恰恰是这个工具最主要的传播方式；②一个 124 KB 的单文件里塞
四块互不相干的功能，改一处要通读全部。

## 版本策略（2026-10-07 修订为四段式）

版本号一律写成 **四段**：`V{a}.{b}.{c}.{d}`。

### 什么时候动哪一位

| 改动的性质 | 动哪一位 | 示例 |
|---|---|---|
| **小更新** —— 纯前端效果，**不碰后端**（加毛玻璃、加懒加载、调间距、换个动效…） | 第 **4** 位 `{d}` +1 | `V0.9.2.0` → `V0.9.2.1` |
| **UI 改动等** —— 界面结构、交互逻辑这类成规模的改动 | 第 **3** 位 `{c}` +1，**`{d}` 归零** | `V0.9.2.0` → `V0.9.3.0` |
| **后端 / 数据层改动** —— 服务端、数据库、引擎、缓存这类 | 第 **2** 位 `{b}` +1，**`{c}`、`{d}` 归零** | `V0.9.2.0` → `V0.10.0.0` |

- 第 **1** 位 `{a}` **还没有规则** —— 要动之前**必须先问用户**。
- 版本号如果写成两段（`V0.9`）或三段（`V0.9.0`），规范形式补零成 **`V0.9.0.0`**。
  **规范形式只有四段这一种。**

### ⚠ 每次动版本号之前，先问用户

不要自己决定这次落哪一档 —— 性质由用户判定，
而且用户可能对这次改动有别的打算（比如想攒着一起发）。**先问，再改。**

### 开发者版本阶段

当前是**开发者版本（beta）**：项目做任何改动都有可能，
所以版本号的意义是"标记这段时间改了什么"，不是"承诺兼容"。
**等正式版本发出来之后清零**（回到 `V0.1.0.0` 并去掉 beta 标记）。

### 落地位置

- 版本号写在**每个页面的 `<meta name="app-version">`** 里
  （`index / app / charter / user / data / settings / privacy / terms / 404`，
  改的时候**一起改**）。
- 各页 `<link href="/css/*.css?v=…">` 的 `?v=` 用**同一个**串 ——
  它是长缓存的版本键（`server.mjs` 只对带 `?v=` 的请求长缓存）。
  ⚠ 只改 meta 不改 `?v=`，样式变更会命中旧缓存 —— "改了看不到"就是这么来的。
- `package.json` 的 `"version"` 去掉 `V` 前缀、保持四段（`0.9.1.0`）。
  ⚠ 四段**不是严格 semver** —— npm 读它不报错（`npm pkg get version` 正常返回），
  但**不要用 `npm version` 来升级**（那是 semver 校验的，会拒）。
  版本一致性由 `smoke-page.mjs` 守，不靠包管理器。
- `tools/smoke-page.mjs` 有三条断言守着：**格式必须是 `V\d+.\d+.\d+.\d+`**、
  **不能是两段/三段**、**各页版本号必须一致**、**`?v=` 必须等于 `app-version`**。
  格式写错或漏改一页，测试会红。
- ⚠ `APP_VER`（页面版本）与 `ENGINE_VER`（算法版本）是**两根轴**：
  后者会写进每一行数据，算法一变所有缓存都要重算。
  改 `APP_VER` 不该动 `ENGINE_VER`，反之亦然。

## 主题与语言（2026-10-07 起）

**双主题**：深 / 浅两套令牌，**语义名完全一致、只换值** —— 页面代码一行不改。
- 切换落在 `<html data-theme="dark|light">`；用户的**选择**另记在 `data-theme-mode`（auto / dark / light）。
- `auto` 由 JS 解析成具体值，CSS 只维护两套 —— 不必为「auto + 系统是浅色」再写第三遍。
- **防闪烁**：每个页面 `<head>` 里有一段**同步内联**脚本，执行早于样式表。
  模块是异步的，等它跑完页面已经按默认色画过一帧了（FOUC）。
  它读的键（`phm_theme`）与 `js/settings.js` 的 `KEYS.theme` 是同一个。
- ⚠ **浅色下主色必须压深**：`#f0b03f` 在白底上的对比度只有约 1.8:1，正文里读不清。
  浅色环境的品牌色是 `#b8791a`（与 `docs.css` 的 `--brand-deep` 同值）。
- 法务文档页（privacy / terms）**跟随主题**，不再固定浅色 ——
  否则从深色的 /app 点进隐私政策会「啪」地闪出一整屏白。

**中英双语**：`js/i18n.js` + `js/i18n/*.js`
- `settings.js` 管**存**，`i18n.js` 管**译**，页面只管调 `t()`。
- 静态 HTML 用 `data-i18n` / `data-i18n-html` / `data-i18n-ph` / `data-i18n-title`，
  加载时 `applyStatic()` 批量替换。
- **JS 渲染出来的内容必须在 `onLangChange` 里自行重绘** —— 静态替换覆盖不到它们
  （导航、设置页的状态文字、表格都是这一类）。
- 默认跟随浏览器语言，用户手动选过就固定住。

#### 字典按页面分片（2026-10-07 收尾时改的）

全站文案合起来 800+ 条。塞进 `i18n.js` 一个文件就是两千多行，
改一句首页文案要在里面翻半天 —— 所以**按页面拆片**：

```
js/i18n.js          ← 只留逻辑（取词 / 应用 / 广播）+ 合并分片
js/i18n/common.js   ← nav.* / c.* / set.theme.* / gloss.* / pg.* / foot.* / tier.* / cell.*
js/i18n/home.js     ← 首页 + 404
js/i18n/app.js      ← 分析工作台
js/i18n/charter.js  ← 谱师页
js/i18n/user.js     ← 玩家页
js/i18n/data.js     ← 数据页
js/i18n/legal.js    ← 隐私政策 + 用户协议
js/i18n/settings.js ← 设置页（set.*）
```

规矩：
- **一个页面一个文件，中英写在同一个文件里**（`{ zh: {...}, en: {...} }`，两段紧挨着）。
  不按语言拆成 `zh.js` / `en.js` —— 那样"改一个词"要开两个文件两处对齐，必然漂移。
- 新增页面：在 `js/i18n/` 建文件 → 在 `i18n.js` 顶部 `import` → **加进 `FRAGMENTS` 数组**。
  忘了走登记，`i18n.js` 就不合并它，等于白翻。
- **重复 key 会在启动时抛错**（合并是 `Object.assign` 语义，重复会静默覆盖；
  宁可崩一下让人看见）。
- ⚠ `js/settings.js` 的 `LABELS` 里存的是**词条名**而不是文案 ——
  那个文件是"存"的层，反向 import i18n 会**循环依赖**（i18n 要 import 它拿语言存取器）。
  所以由页面调 `t(r.labelKey, r.vars)`。
- ⚠ 像 `RKS_NOTE` 这种**导出的常量字符串**是 i18n 的天敌：常量在语言变化时不会变。
  要么改成函数（`rksNote()`），要么让调用方在渲染时现取。

**防回退**：`tools/lint-i18n.mjs`（确定性、不需要浏览器）
- 分片是否都登记了 / zh-en 键集合是否对称 / **源码引用的 key 是否真的存在**
- 反向查僵尸词条（字典里有、没人用 —— 通常是翻完忘了接，或删代码留下的）
- 为什么不用无头浏览器查"页面残留中文"：DOM 上的中文分不清"漏翻"和"数据"
  （曲名、谱师名本来就是中文），必然误报。改成查**词条引用**就精确了。
- 渲染层的抽查在 `tools/verify-pages.mjs` 的 `[12]`：真的去点页脚语言开关、
  刷新后不能退回中文、每页在英文模式下不能残留已知的中文 UI 短语。

> ⚠ **模块引用路径必须统一（模块之间都不带 `?v=`）**。
> ES 模块之间是相对 `import`（`./ui.js`）；如果页面又用 `/js/ui.js?v=…` 引用同一个文件，
> 浏览器会当成**两个不同的模块实例**，于是两份状态分裂 ——
> 真踩过：设置页切了语言，`ui.js` 里的导航不跟着变。
> 所以 `server.mjs` 只对**带 `?v=`** 的请求长缓存；不带查询串的 js / json 走 `no-cache`
> （每次协商，命中就是 304，开销很小）。
> 例外是 `engine.js` 与 `data/ref-com.json`：它们只在**单一位置**引入，
> 且换代时必须立刻拿到新内容，所以保留 `?v=`。

干净 URL（`/app` 而不是 `/app.html`）由 `server.mjs` 里一张**显式映射表**提供，
且映射目标必须在 `PUBLIC_FILES` 白名单里 —— 加页面必须同时改两处，
不会因为"忘了写路由"而意外暴露文件。

共享模块：

| 文件 | 内容 |
|---|---|
| `css/base.css` | 主题令牌（深/浅两套）+ 导航 + 按钮/表格/卡片/状态条。**令牌的唯一来源** |
| `css/docs.css` | 法务长文档的排版（浅色为主、也可以跟随深色）。与 base.css **分开**：文档是阅读场景，不是应用界面 |
| `js/settings.js` | 用户设置的**唯一真源** —— 键名 / 默认值 / 读写 / 清理只在这里定义 |
| `js/i18n.js` | 中英字典 + `t()` + `data-i18n` 批量替换 + 语言切换广播 |
| `js/phira.js` | Phira 公开 API 客户端。所有接口陷阱的实测结论都写在文件头 |
| `js/ui.js` | 导航渲染、转义、格式化、共享定数缓存读取、P.H.M. RKS |
| `js/engine.js` | （见下）纯计算，不碰 DOM/网络 |
| `js/sharecard.js` | 分享卡片绘制 |

## 分页（2026-10-07 起，全站统一的硬要求）

**为什么必须分页**：原来「看全库」的唯一办法是 `limit=100000` 一次拉回来。
649 行还行，几万行就是几十 MB 的响应 + 浏览器全量渲染 ——
分页不是"好看"，是**库变大之后还能用**。

### 三处列表，各自的真实上限

| 列表 | 数据源 | 分页方式 |
|---|---|---|
| 站点定数缓存 | 自己的云数据库 | **服务端真分页**：`limit/offset` + `Prefer: count=exact` 拿真总数 |
| 谱师作品 | `/chart?search=` 翻页后本地按 charter 筛 | **Phira 侧翻页**（30/页，count 真实）+ 累加后**前端分页**展示 |
| 单谱全服记录 | `/record/query/{id}` | **Phira 侧翻页**（30/页，按分数降序，count 真实） |
| 玩家最近成绩 | `/record?player=` | ❌ **不能分页** —— 服务端忽略 page/pageNum，恒 20 条。只能如实说明 |

### 实现要点

- `lib/cloud.mjs` 的 `dbPageCharts()`：**排序字段必须走白名单**（`SORTABLE`）。
  它直接拼进 PostgREST 的 `order=`，不挡就是把查询表达式交给调用方。
  服务端再挡一次（`/api/charts?page=1&sort=password` → 400）。
- `dbFetch()` 现在会把 **`content-range`** 带出来。没有它就没有总数，
  前端做出来的页码是**假的** —— 这一条是分页能不能信的前提。
- 页码窗口策略：首尾 + 当前±2，中间 `…` 省略。649 行 / 每页 10 条 = 65 个页码，
  不省略工具栏会被撑爆。
- `js/ui.js` 的 `pagerHTML()` / `wirePager()` 是**全站唯一**的分页器实现
  （数据页 / 谱师页 / 玩家页共用）。各写一份必然长成三个样子。
- 数据管理页把当前视图（页码/排序/过滤）**同步进 URL**（`replaceState`，
  不是 `pushState` —— 否则每翻一页都塞一条历史，返回键就废了），
  于是"第 7 页、只看 AT、按社区共识降序"可以直接分享。

### 分页必须被测试证明

分页最容易糊弄的形态是「画了页码、点了没反应」。
所以 `tools/verify-pages.mjs` 里每一条分页断言都**比对内容**：

- 翻到第 2 页后，本页的 chart_id 集合与第 1 页**零重叠**（不是"有按钮"）
- 翻页后总数**不变**
- 过滤后总数**变小**
- 非法排序字段被**服务端**拒绝（400），而不是前端崩

## 四个层次，各自只干一件事## 四个层次，各自只干一件事

| 层 | 位置 | 职责 | **不做什么** |
|---|---|---|---|
| 引擎 | `public/js/engine.js` | 解析 ZIP（RPE/PGR/**PEC**）、算特征、双参照 k-NN 定数 | 不碰 DOM / 存储 / 网络 |
| 参照集 | `public/js/ref-official.js` + `public/data/ref-com.json` | **唯一真源是 `tools/gen-ref.mjs`**；输出物不要手改 | 不放算法，只放数据 |
| 云端访问 | `lib/cloud.mjs` | 数据库地址、publishableKey、**写入凭据（三路加载）**、`dbFetch` / `dbPutChart` / `dbPutScores` / `dbListStale` | 不写业务逻辑 |
| 参照集读取（Node） | `lib/refstore.mjs` | 服务端读 `ref-com.json` 供 `review.mjs` 使用 | 读不到就抛错，**不静默降级** |
| 网关 | `server.mjs` | 路由、字段校验、限流、静态托管 | 不写业务算法，不直接碰数据库配置 |
| 界面 | `public/*.html`（见上面站点结构表） | 渲染、交互、调 API | 不做可信判定 |
| 出图 | `public/js/sharecard.js` | 把结果画成 PNG（横 1200×630 / 竖 1080×1920） | 不加载任何外部图片（会污染 canvas） |

`lib/review.mjs`（服务端复核）与 `tools/`（离线工具）是横切件，按需引用上面几层。

> **为什么把云端访问单独抽出来**：`tools/warm-cache.mjs` 这类离线脚本也要写库，
> 如果数据库地址与凭据长在 `server.mjs` 里，工具就得复制一份 —— 两份迟早会漂移。
> 现在只有 `lib/cloud.mjs` 知道「怎么跟数据库说话」，其余文件都只管自己的事。

## 输出的契约：**永远给「数字 + 它的不确定度」**

这是这个项目唯一不能妥协的产品约束，也是它敢叫「不判定虚标」的底气。

一次 k-NN 会得到 20 张参照谱。取**加权截尾均值**（去掉按定数排序后首尾各 15% 权重）
作为点估计；它们的定数**跨度**就是不确定范围。

> v0.5.0 把聚合从「加权中位」换成了「加权截尾均值」——
> 中位误差 0.500→0.453、均值误差 0.820→0.816 都变好，
> 同时输出分辨率从 **104 个不同数字**提到 **1332 个**（整数占比 14.6%→0.0%）。
> 原因与四方案对比见 [`ENGINE-EXPERIMENT.md`](ENGINE-EXPERIMENT.md)。

**而且是两个标度一起给** —— 这是 2026-10-07 之后的核心设计：

| 标度 | 参照集 | 含义 |
|---|---|---|
| **社区共识**（主结果） | 9,508 张 Phira 社区谱 | 站内谱师实际定价的共识 —— 谱师会拿自己看到的数来对照 |
| **官谱标度** | 1,037 张 Phigros 官谱 | 与官方一致的绝对标度，可查证 |

为什么不只印一个：官谱与社区谱**结构分布不同**（社区谱定数中位 15.1 / 官谱 10.6，
长条占比只有官谱的 1/3）。只印官谱标度，社区谱师会看到「我的 IN 14 被算成 11.6」
——那不是算错，是**两个标度本来就差这么多**。把差距印出来，争议就变成了信息。
实测（1,367 张留出）：社区标度 |偏差| 中位 0.453 · 均值 0.816 / ≤1.0 命中 81.8%；
官谱标度 1.187 / 67.0%。

完整方法与所有被否掉的方案（含 osu! 式 strain 曲线的负面结果）见
[`ENGINE-EXPERIMENT.md`](ENGINE-EXPERIMENT.md)。

⚠ **参照集里装着被测谱自己** → 已知 chart_id 时必须传 `excludeId`。
不排除就是距离 0 的自匹配，返回"它自己的声明值"，整个工具退化成橡皮图章
（而且误差看起来是完美的 0.00，非常隐蔽）。

⚠️ **只印中点等于假装精确。** 第一张的范围上限 14.5 就贴着它的标称 14.6 ——
模型其实在说「我不确定」，而界面如果只写 11.6，就会变成「你说我谱只有 11.6」。
所以：**结果卡片、分享卡片、任何对外的地方都必须带上范围**；
跨度 ≥3 时还要额外说明「这张谱的结构在官谱里没有紧密对应物」。

改 `sharecard.js` / 卡片渲染时，这条是硬要求，不是为了好看。

**分界线**：凡是「不可信输入 + 需要可信输出」的计算，都在网关侧做。
凡是「即时反馈 + 隐私」的计算，都在浏览器侧做。

## 为什么用同一份引擎

`public/js/engine.js` 被**两端同时 import**：浏览器用 `<script type="module">`，
Node 用 `import { analyzeChart } from '../public/js/engine.js'`。

好处有三：

1. **防投毒**：服务端能用与客户端**完全相同的算法**复算，比对才有意义
2. **不会漂移**：不存在「前端一套、后端一套」两个实现逐渐走偏的问题
   （这个项目早期就有过 Python 版与 JS 版算法不一致的历史教训）
3. **改一处即两端生效**：修了 bug 不会只修好一半

代价：引擎必须保持纯计算，不能依赖任何一端专有的 API。

## 数据流：一条定数怎么进库

```
① 客户端本地算完，得到 {chart_id, ref_const, nps, ...}
       ↓  POST /api/contribute
② 网关字段校验（范围、必填、长度）
       ↓
③ 查 phm_charts 是否已有该 chart_id
       有 → 直接跳过（不重复下载，客户端改不动已有权威值）
       没有 ↓
④ lib/review.mjs：
       向 Phira 要 file 地址 → **服务端下载谱面包** → 跑引擎 → 得到权威值
       ↓
⑤ 与客户端提交值逐字段比对（容差见 TOL）
       一致 → 正常
       不一致 → 记录 mismatched，**但仍然写服务端算的值**
       ↓
⑥ 调 phm_put_chart(secret, row) —— 落库（engine_ver = "server-verified"）
```

**关键点在第 ⑤ 步**：客户端值不一致**不是**拒绝写入的理由 ——
只说明客户端引擎过期了（用户没刷新页面）。
正确做法是「不采信它的值，但用服务端算出的值入库」，这样不丢数据。

⚠ **但这只解决了「走网关」这条路。** 攻击者可以直接 POST 到 REST 端点，
完全跳过上面五步。所以真正的门在第 ⑥ 步：表级写权限已撤销，
落库只能经 `phm_put_chart()`，而它要求带上**只有服务端才有的写入凭据**。
细节见 `SECURITY.md`「防投毒」一节 —— 那里记了三代修复的过程。

## 为什么客户端没有"直连数据库"的退路

早期版本里 `/api/*` 失败会回退成浏览器直连数据库。**这是错的**，两个原因：

1. **网关不再是边界** —— 客户端保留了一条能绕开校验和限流的写库路径
2. **故障放大** —— 服务端过载 → 请求失败 → 客户端改打数据库 → 数据库更忙
   → 更多失败 → 更多客户端切换退路，形成自我放大的重试风暴

现在的策略：**失败就失败**。上传失败不影响本机结果 ——
定数已经算出来显示在卡片上了，用户该看到的都看到了。

## 静态资源的暴露范围

只有 `public/` 下的内容可能被送出，且再经过一层白名单：

- 根文件：`index.html` / `privacy.html` / `robots.txt` / `favicon.ico`
- 子目录：仅 `js/`、`css/`、`data/`，且扩展名必须是
  `.js .css .json .png .svg .ico .webp .woff2`
  （`data/` 只放参照集生成物 `ref-com.json`，不放别的）
- 文本类响应**按需 gzip**（`index.html` 124 KB → 43 KB，`ref-com.json` 751 KB → 353 KB），
  压缩结果按 mtime 缓存

源码（`server.mjs` / `lib/`）和运行时数据（`server-store.json`）都在
`phm-web/` 根下、`public/` 之外，**天然不可达**。

> 历史事故：早期只做了「路径不以 ROOT 开头就拒」，把目录穿越防护
> 当成了白名单，结果 `server.mjs`（含数据库地址与密钥）和
> `server-store.json`（含真实访客 IP）被公开下载。
> **目录穿越防护 ≠ 白名单。**

## 部署形态

WorkBuddy 托管，单端口 HTTP 服务：

- 平台注入 `PORT` 环境变量，服务必须绑 `0.0.0.0`
- 沙箱内**只有文件存储**可用（无外部数据库进程）
- 服务端文件**不跨部署保留** → 因此 `server-store.json` 只存可重建的数据
  （限流计数），权威数据一律在云数据库
- 域名与云服务 Origin 在重新发布时保留 → 云登录继续可用

写入凭据的**三条路**（先命中者胜，启动时会打印用的是哪一条）：

1. 环境变量 `PHM_WRITE_SECRET`
2. `phm-web/.env`（已 gitignore；模板见 `.env.example`）
3. `phm-web/write-secret.txt`（已 gitignore）

三条都没有 → 定数照常能算，但写不进缓存（`cacheWrite.ok=false`）。
这是有意的 **fail-closed**：宁可不缓存，也不开一条没凭据的写后门。

发布：用 `sites` 能力发布 `phm-web/` 目录。

发布前建议跑一遍（`--net` 需要联网）：

```bash
node tools/gen-ref.mjs --check     # 参照集与真源是否同步
node tools/verify-engine.mjs       # 引擎 44 条断言
PORT=5199 node server.mjs &        # 另开一个终端
node tools/smoke-page.mjs http://127.0.0.1:5199   # 真页面冒烟
```

## Phira 接口的硬限制（不是我们的 bug，是必须讲清楚的事实）

全部实测过（`/openapi.json` 有规范，但**规范里有参数 ≠ 处理器认这个参数**）：

| 想要 | 实际能拿到 | 结论 |
|---|---|---|
| 某个玩家的**全部**成绩 | `/record?player=` **恒返回最近 20 条**；`page` / `pageNum` 在规范里写着，但被服务端忽略（实测 `page=0/1/2/5` 与 `pageNum=100` 返回的 20 个 id **完全相同**） | 拿不到全量，只能拿最近 20 |
| 某张谱上**我**的成绩 | `/record?player={uid}&chart={cid}` ✅ **不受 20 条限制** | 绕过上一条的办法之一，`/user` 页做成了入口 |
| 某张谱的**全服记录** | `/record/query/{chartId}` ✅ 可翻页，返回 `{count, results}`。⚠ `page` 是 **1-based**（`page=0` 时 `results` 为空但 `count` 照给）、`pageNum` **≤30**（31+ 报 `Too many entities in one page`） | 本站唯一能拿"全谱库"的端点；`count` 是真总数，可以做真分页 |
| 某张谱的 **TOP15** | `/record/list15/{chartId}` ✅ 无需认证（id 是 chart id），带 `best: true` 标记 | **尚未在产品里使用** —— 做"顶尖成绩"或难度校准都是现成的 |
| 某张谱**我的最好成绩** | `/record/best/{chartId}` ❌ 返回 `UNAUTHENTICATED` | 要登录。公开工具用不了，因为**我们不要用户的 Phira 凭据** |
| 某个谱师的**全部**作品 | ⭐ **`/chart?uploader={uid}` 是服务端精确过滤**（实测 `uploader=257272` → `count=2`，两条记录的 uploader 都等于 257272）。⚠ 只能单账号、不能与 `search=` 组合（组合返回空响应体）；`pageNum` 上限同为 30 | 用账号 id 取作品是**正解**（见下） |
| 按**谱师文本**找作品 | `/chart?search={名}` 分页有效（30/页），但**同时匹配 name + charter + description**；`?charter=` / `?author=` / `?userId=` 都不存在（静默忽略，返回全量 9691 条） | 只能当兜底，且必须按命中字段分类展示 |

### 「谱师搜不到」的根因与现在的做法（2026-10-07）

用户反馈「输入谱师名，搜不到他的作品」。实测拆出**三个叠在一起的原因**：

1. **charter 是自由文本**。真实案例：作者账号叫「平方秒和立方吨」，
   但他的谱面 `charter` 字段写的是 **`SqrtSecond Chart Team`**（团队名）。
   拿名字去比 charter，必然一条都命中不了。
2. **`/chart?search=` 还匹配 description**。实测搜「平方」返回 59 条，
   绝大多数是**别人的谱面在说明里感谢他**（例：`Eviternity` 的 description
   写着「特别感谢b站@平方秒与立方吨」）—— 一条都不是他的作品。
3. **中文近形字**。作者本体是「平方秒**和**立方吨」(id 257272)，
   而 `/user?search=平方秒与立方吨` 只返回 2 个**同名仿号**（id 1796076 / 2789680，
   两人名下 **0 张谱**）。搜「平方秒」才能找到本体。
   ⚠ `/user?search=` 是**子串**匹配且**忽略 page**（实测第 1 页与第 2 页返回同一批）。

现在的做法是**两步走**，并在页面上把两件事分开说清楚：

```
①  /user?search={名}      →  候选**账号**（带 id）      ← 一行一个按钮，让用户点
②  /chart?uploader={id}   →  他**上传**的谱面，精确     ← 主结果
③  /chart?search={名}     →  兜底：按 charter 文本找     ← 分三档：
                               charter 完全相同 / charter 包含 / 仅在 description 提到
                               最后一档明确标注「不是他的作品」
```

第 ③ 档的分档不是锦上添花 —— 用户搜自己名字被 59 条不相干结果淹没，
正是"搜不到"这个体感的直接来源。把噪声**标出来**比把它藏起来更有用。

> 这些结论全部固化在 `public/js/phira.js` 的文件头「陷阱清单」里（第 18~20 条），
> 并由 `tools/verify-pages.mjs` 用真浏览器驱动 UI 验证。

**缺口有多大（实测）**：UID 2 的 `numRecords` 是 **375**，而一次
`/record?player=2` 只给 **20** 条。逐张谱查（`/record?player=&chart=`）能把
"最近 20 条"之外的记录捞回来（抽样 25 张 Ranked 谱就多找到 1 张），
但约 **2 秒/张**，覆盖全部上架谱要跑几分钟 ⇒ 只适合做成**按需**的深度分析。

**能不能真的改上游？** 分三种，结论不同：

1. **提 PR 改 API —— 不行。** `TeamFlos/phira` 仓库里只有**客户端**
   （`phira` / `phira-main` / `prpr-*` / `phira-monitor`），
   **处理 `api.phira.cn` 的服务端不在里面** —— 它是闭源的。所以没有可以改的代码。
2. **提 issue 反馈 —— 可行，而且有据可依。** 仓库里 19 个含 "record" 的 issue
   全是客户端问题，**没人提过分页失效**。论证是硬的：OpenAPI 规范给 `/record`
   声明了 `page` / `pageNum`，而**同族的 `/record/query/{chartId}` 明确实现了分页**
   ⇒ 这是**实现遗漏**，不是产品决策。渠道：GitHub issue（`phira-docs` 适合提
   规范与实现不一致）+ Phira 官方 QQ 频道。
3. **自建主站 —— 不行**（同上，服务端不开源）。但**自建缓存层是可行的**，
   本站已经在做（定数缓存），可以再扩展到成绩快照。

另外两条会直接影响用户观感的：

- **官方 RKS / B19 已停摆**：实测抽样 10 位今天仍在游玩的玩家，bestPool 里最新一条
  全部停在 2023 ~ 2026-03；2026 年后注册的账号从一开始就是空的。
  所以本站另算一个 **P.H.M. RKS**（公式与 Phigros 官方一致，用老玩家 bestPool 反推验证过），
  并如实标注它是"替代值、通常偏低"，绝不冒充官方值。
- **用户名搜索的 `count` 字段是坏的**：`/user?search=X` 返回 `{count:0, results:[...]}`。
  ⇒ 判断"有没有找到"永远看 `results.length`，不看 `count`。

> 这些结论全部固化在 `public/js/phira.js` 的文件头「陷阱清单」里，
> 并由 `tools/verify-pages.mjs` 用真浏览器驱动 UI 验证。

|---|---|---|
| 写入凭据的部署前提 | 三条路都要么靠环境变量、要么靠"部署时带上非 git 跟踪的文件"；都没有则写不进缓存（可观测：`cacheWrite.ok=false`，启动日志也会写明来源） | 已补 `.env` + `.env.example`；托管侧若有环境变量入口则更稳 |
