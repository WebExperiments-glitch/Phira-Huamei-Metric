# 架构

## 一张图

```
┌──────────────────────────────────────────────────────────┐
│ 浏览器                                                    │
│                                                          │
│  index.html（UI + 交互 + Phira 调用 + 账号）              │
│      │                                                   │
│      └─ /js/engine.js  ← 本地解析谱面，文件不出浏览器      │
│                                                          │
└───────┬──────────────────────────────┬───────────────────┘
        │ 只传结构特征 + chart_id        │ 只读公开资料
        ▼                              ▼
┌───────────────────────┐      ┌──────────────────┐
│ Node 网关 server.mjs  │      │ api.phira.cn     │
│  校验 / 限流 / 路由   │      └──────────────────┘
│         │             │
│         └─ lib/review.mjs                          ← 服务端**自己下载谱面**
│              │  用 /js/engine.js 复算               （服务端不受 CORS 限制）
│              │  与客户端提交值比对
│              │  **落库值永远取自服务端计算结果**
└───────┬───────────────┘
        ▼
┌───────────────────────┐
│ WorkBuddy 云数据库     │
│ phm_charts（定数缓存）  │
│ phm_scores（成绩数据）  │
│ phm_profiles（账号档案）│
└───────────────────────┘
```

## 四个层次，各自只干一件事

| 层 | 位置 | 职责 | **不做什么** |
|---|---|---|---|
| 引擎 | `public/js/engine.js` | 解析 ZIP（RPE/PGR/**PEC**）、算特征、k-NN 定数 | 不碰 DOM / 存储 / 网络 |
| 云端访问 | `lib/cloud.mjs` | 数据库地址、publishableKey、**写入凭据**、`dbFetch` / `dbPutChart` / `dbPutScores` | 不写业务逻辑 |
| 网关 | `server.mjs` | 路由、字段校验、限流、静态托管 | 不写业务算法，不直接碰数据库配置 |
| 界面 | `public/index.html`（中文）/ `public/en.html`（英文） | 渲染、交互、调 API | 不做可信判定 |
| 出图 | `public/js/sharecard.js` | 把结果画成 PNG（横 1200×630 / 竖 1080×1920） | 不加载任何外部图片（会污染 canvas） |

`lib/review.mjs`（服务端复核）与 `tools/`（离线工具）是横切件，按需引用上面几层。

> **为什么把云端访问单独抽出来**：`tools/warm-cache.mjs` 这类离线脚本也要写库，
> 如果数据库地址与凭据长在 `server.mjs` 里，工具就得复制一份 —— 两份迟早会漂移。
> 现在只有 `lib/cloud.mjs` 知道「怎么跟数据库说话」，其余文件都只管自己的事。

## 输出的契约：**永远给「数字 + 它的不确定度」**

这是这个项目唯一不能妥协的产品约束，也是它敢叫「不判定虚标」的底气。

一次 k-NN 会得到 20 张参照官谱。它们的定数**跨度**就是这个结论的不确定范围：

```
#25818 蛍はいなかった（IN 14.6）  中点 11.6   范围 9.5–14.5
#16578 Secret of my heart （14.3） 中点  9.7   范围 4.5–13.1
#22681 Pandemic            （15.3） 中点 16.6   范围 15.6–17.9  ← 邻居集中，结论硬
```

⚠️ **只印中点等于假装精确。** 第一张的范围上限 14.5 就贴着它的标称 14.6 ——
模型其实在说「我不确定」，而界面如果只写 11.6，就会变成「你说我谱只有 11.6」。
所以：**结果卡片、分享卡片、任何对外的地方都必须带上范围**；
跨度 ≥3 时还要额外说明「这张谱的结构在官谱里没有紧密对应物」。

改 `sharecard.js` / 卡片渲染时，这条是硬要求，不是为了好看。

**分界线**：凡是「不可信输入 + 需要可信输出」的计算，都在网关侧做。
凡是「即时反馈 + 隐私」的计算，都在浏览器侧做。

## 为什么用同一份引擎

`public/js/engine.js` 被**两端同时 import**：浏览器用 `<script type="module">`，
Node 用 `import { analyzeChart } from '../public/js/engine.js'`。

好处有三：

1. **防投毒**：服务端能用与客户端**完全相同的算法**复算，比对才有意义
2. **不会漂移**：不存在「前端一套、后端一套」两个实现逐渐走偏的问题
   （这个项目早期就有过 Python 版与 JS 版算法不一致的历史教训）
3. **改一处即两端生效**：修了 bug 不会只修好一半

代价：引擎必须保持纯计算，不能依赖任何一端专有的 API。

## 数据流：一条定数怎么进库

```
① 客户端本地算完，得到 {chart_id, ref_const, nps, ...}
       ↓  POST /api/contribute
② 网关字段校验（范围、必填、长度）
       ↓
③ 查 phm_charts 是否已有该 chart_id
       有 → 直接跳过（不重复下载，客户端改不动已有权威值）
       没有 ↓
④ lib/review.mjs：
       向 Phira 要 file 地址 → **服务端下载谱面包** → 跑引擎 → 得到权威值
       ↓
⑤ 与客户端提交值逐字段比对（容差见 TOL）
       一致 → 正常
       不一致 → 记录 mismatched，**但仍然写服务端算的值**
       ↓
⑥ 调 phm_put_chart(secret, row) —— 落库（engine_ver = "server-verified"）
```

**关键点在第 ⑤ 步**：客户端值不一致**不是**拒绝写入的理由 ——
只说明客户端引擎过期了（用户没刷新页面）。
正确做法是「不采信它的值，但用服务端算出的值入库」，这样不丢数据。

⚠ **但这只解决了「走网关」这条路。** 攻击者可以直接 POST 到 REST 端点，
完全跳过上面五步。所以真正的门在第 ⑥ 步：表级写权限已撤销，
落库只能经 `phm_put_chart()`，而它要求带上**只有服务端才有的写入凭据**。
细节见 `SECURITY.md`「防投毒」一节 —— 那里记了三代修复的过程。

## 为什么客户端没有"直连数据库"的退路

早期版本里 `/api/*` 失败会回退成浏览器直连数据库。**这是错的**，两个原因：

1. **网关不再是边界** —— 客户端保留了一条能绕开校验和限流的写库路径
2. **故障放大** —— 服务端过载 → 请求失败 → 客户端改打数据库 → 数据库更忙
   → 更多失败 → 更多客户端切换退路，形成自我放大的重试风暴

现在的策略：**失败就失败**。上传失败不影响本机结果 ——
定数已经算出来显示在卡片上了，用户该看到的都看到了。

## 静态资源的暴露范围

只有 `public/` 下的内容可能被送出，且再经过一层白名单：

- 根文件：`index.html` / `privacy.html` / `robots.txt` / `favicon.ico`
- 子目录：仅 `js/`、`css/`，且扩展名必须是 `.js .css .png .svg .ico .webp .woff2`

源码（`server.mjs` / `lib/`）和运行时数据（`server-store.json`）都在
`phm-web/` 根下、`public/` 之外，**天然不可达**。

> 历史事故：早期只做了「路径不以 ROOT 开头就拒」，把目录穿越防护
> 当成了白名单，结果 `server.mjs`（含数据库地址与密钥）和
> `server-store.json`（含真实访客 IP）被公开下载。
> **目录穿越防护 ≠ 白名单。**

## 部署形态

WorkBuddy 托管，单端口 HTTP 服务：

- 平台注入 `PORT` 环境变量，服务必须绑 `0.0.0.0`
- 沙箱内**只有文件存储**可用（无外部数据库进程）
- 服务端文件**不跨部署保留** → 因此 `server-store.json` 只存可重建的数据
  （限流计数），权威数据一律在云数据库
- 域名与云服务 Origin 在重新发布时保留 → 云登录继续可用

发布：用 `sites` 能力发布 `phm-web/` 目录。

## 已知的架构局限

| 局限 | 影响 | 出路 |
|---|---|---|
| 写入凭据依赖本地文件 | 部署时若没带上 `write-secret.txt`，定数照常可算但写不进缓存（可观测：`cacheWrite.ok=false`） | 改用环境变量 `PHM_WRITE_SECRET`（已支持且优先），需要托管侧入口 |
| 缓存被篡改无自动发现 | 凭据泄露的话，写进去的假定数不会被发现 | 定期抽样 `recompute()` 对账（表很小，全量重算只要几十秒） |
| 服务端复核有成本 | 每张**新**谱要下载一次谱面（约 1.7s / 几 MB） | 已缓存直接跳过；未来可加队列 |
| 前端仍是单文件 | `index.html` 约 104KB，无法按组件单测 | 可继续拆为多个 module |
| 无 CI | 改动质量依赖人工验证 | 待补（至少把引擎真实执行脚本接进去） |
