# 自动写谱（MP3 → 规则谱面）v1.4

> 用户只做一件事：**导入 MP3**。难度由系统判定，用户不能手动选择。
> BPM、时长、拍点、踩音点、段落能量全部自动提取；生成 **.pez**（ZIP）或 **.zip**。
> 全程浏览器本地，音频不上传。

## 1. 输入与自动提取

页面：`/rulechart`；代码：`public/js/audio-analysis.js` + `public/js/rulechart.js`。

```text
MP3/WAV/OGG/FLAC/M4A
  → decodeAudioData（浏览器）
  → 单声道 22050Hz
  → STFT(1024/512) → 谱通量 onset envelope
  → 自相关估 BPM（60–200，折叠到 80–180）
  → 60–200 BPM 网格搜索 + 半拍/IOI 中位数修正（避免 190 被误判成 152/95）
  → 分频段：低频 kick / 高频噪声 + 谱平坦度 → 鼓点
  → 中频谐波 + 低平坦度 → 钢琴/旋律点
  → 峰值踩音（time / strength）
  → RMS 分段（intro / verse / chorus / outro）
```

页面上直接显示：BPM、时长、拍点数、总踩音点、**鼓点**、**钢琴点**、段落能量。**没有 BPM/时长/密度输入框。**

排谱时：钢琴点不少于鼓点 80% → 用钢琴点；否则用鼓点；两者都没有才回退总 onset。

## 2. 2K 的含义：2 指可打，不是 2 条固定轨道

2K 指“最多两根手指可以完成”。参照 `_research/refs/pont`（charter: RuleEngine）：
**1 条判定线固定在 X=-300、Y=200；2 指自由分散（左右手各半屏交替）、一次一个、无和弦、无 Hold**。

## 3. 时间轴：拍网格 → 量化（**不是"吸到 1/4 网格"**）

原始频谱峰值不等于"拍点"。而且**检测到的 onset 时间也不能直接当音符时间** ——
检测误差 ±20ms 起，直接铺出来的音符会落在 0.47 / 0.94 拍这种位置：
判定线按拍走，玩家读不出来，只能靠背。

所以时间轴分三步（`public/js/rhythm.js`）：

1. **建拍网格**：`buildGrid()` → BPM + 相位 + 小节（默认 4 拍）
2. **相位精调** `refinePhase()`：上游给的相位精度只到**半拍**
   （它是在半拍网格上估的）。实测一段 120BPM、每拍一个 kick 的音频，
   网格相位会偏 0.25 秒 —— 于是**所有音符落在"半拍"上**，小节头全错位。
   精调在 ±半拍内按 2ms 步长扫描，用强度加权贴合度取峰值。
3. **量化** `quantizeOnsets()`：把每个 onset 吸附到**可读时值**

### 可读时值的层级与代价

| 层级 | 含义 | 读谱成本 |
|---|---|---|
| 1/1 | 整拍 | 0 |
| 1/2 | 八分 | 22 |
| **1/3** | **三连音** | 38 |
| 1/4 | 十六分 | 50 |
| **1/6** | **六连音** | 78 |

选择规则：`代价 = |实际偏差ms| × devWeight + 该层级成本`，取最小且偏差在容差内的那个。

- **三连音不会被打成两个音 + 一个空拍** —— 1/3 与 1/6 在层级表里。
- **简单读法优先** —— 半拍位置（偏差 0 + 成本 22）不会被吸到 1/3（38）。
- **偏太远直接丢** —— 容差 40ms。丢掉比硬吸好：硬吸出来的音谁也打不准。

> ⚠ **层级表故意不含 1/8（三十二分）**。
> 1/8 格宽 0.125 拍，半格只有 0.0625 拍，比任何合理容差都小 ——
> 有了它「任何时间点都能被吸到某个格子」，容差形同虚设，量化失败不可能发生。

> ⚠ 容差必须**小于最细网格的半格**（1/6 半格在 120BPM 下约 42ms），否则同理。

### 三连音的识别与标记

`markTuplets()` 把连续 ≥3 个落 1/3 的组标成三连音，报告里能报出来。
⚠ 组尾常常正好落在整拍上（4+1/3 → 4+2/3 → **5.0**），
判定要允许"下一个音是整拍"，否则每组都被截断、永远成不了组。

## 3.5 事件选择：检测到声音 ≠ 应该放音符

`public/js/salience.js`。以前是「选一个 onset 源 → 按 targetNps 截断或补齐」，
其中**补齐那一步会凭空造音符**（`beats[i] + s * beatSec / 4`）：
那段音频里根本没有那个声音，玩家打到的是一张假谱。

现在的做法：

1. **三个声部都进候选池**（鼓 / 旋律 / 混合 onset）。
   以前是二选一（piano 多就只用 piano），等于丢掉一半音乐信息 ——
   鼓点给骨架、旋律给重音，两者互补。
2. **打音乐显著性分**：

   ```text
   base = 0.35 + 0.65 × strength          ← 强度是下限
   s    = base × (0.55 + 0.45 × 拍位权重) × (0.70 + 0.30 × 声部权重)
   ```

   ⚠ 是**乘子结构，不是加权求和**。求和的问题：各因子互相补偿 ——
   实测一个 strength 0.03 的 1/8 噪声靠"小节头 + 声部"就能凑到 0.345 越过阈值。
   乘子结构里强度是下限，几乎没有能量的东西拍位再好也高不了。

   拍位权重再乘一个**细分折扣**（整拍 ×1.0 → 1/8 ×0.46）：
   小节头上的 1/8 噪声不该和整拍鼓点同权。

   加分项：乐句起点 +0.10、节奏型重复（前后 2 小节内同签名 ≥2 次）+0.08。
   减分项：弱起（小节线前 1 拍内的非整拍）−0.06 —— **降权但不删**，那是真实写法。

3. **按分数选到目标数量，但有阈值下限**（0.26–0.34 按难度）。
   **候选不够就少给**，`shortfall` 如实上报给页面：
   「你要 3.6 NPS，这首歌只有 1.9 NPS 的音乐事件」是信息；
   悄悄补齐成 3.6 才是骗人。

4. **映射到判定线**：按「哪只手更空」分配（记录每手的占用时间），
   不是 `i % 2` 机械交替 —— 机械交替会在长音后出现"一只手连打 8 个"。
   同侧连续上限 6。

## 4. 难度由系统判定（用户不可选）

`detectDifficulty(analysis)` 用音频特征估算“潜力 NPS”：

```text
potential = onsetRate×1.55 + energy×1.8 + avgCentroid×0.8
          + avgStrength×0.9 + BPM偏离×0.8 + 0.6
```

判档阈值（按 Pont IN13 / 诀别书 IN11.8 校准）：`<4.0 EZ / <4.75 HD / <5.8 IN / ≥5.8 AT`。
目标 NPS：EZ 3.6 / HD 4.4 / IN 4.9 / AT 6.1。
页面只显示「系统判定：IN 14 · 潜力 6.5 NPS（踩音 2.9/s · BPM 120.2）」，
**没有难度按钮**。这样避免用户随意选一个不匹配音频的难度。

### 2.1 预设（系统内部使用）

| 难度 | Level | 目标 NPS | 细分 | 同轨最小间隔 | 和弦上限 | 轨道 | 判定线 |
|---|---|---|---|---|---|---|---|
| EZ | EZ 7 | ~3.6 | 4 | 0.25 拍 | 1 | 左右半屏 | 1 主 |
| HD | HD 11 | ~4.4 | 4 | 0.25 拍 | 1 | 左右半屏 | 1 主 |
| IN | IN 14 | ~4.9 | 4 | 0.25 拍 | 1 | 左右半屏 | 1 主 |
| AT | AT 16 | ~6.1 | 4 | 0.25 拍 | 1 | 左右半屏 | 1 主 |

- 当前 2 指可玩模式：Tap 85% / Drag 15%；**不出 Hold/Flick**，避免长条与蓝键重叠。
- 段落能量决定密度：intro 低、chorus 高；踩音强度越高越优先保留。
- 强拍（4 的整数倍）按概率加和弦，且必须换轨。
- 生成后按目标 NPS 补齐/收敛，避免 EZ 过空、AT 过稀。

### 2.1 依据：9,684 张真实 Phira 谱面

从 `data/community.jsonl` 统计（按难度分段）：

| 难度段 | 中位 NPS | 中位物量 | 中位判定线数 | Tap / Hold / Flick / Drag |
|---|---|---|---|---|
| 7–10 | 4.07 | 614 | 24 | 48.1 / 9.0 / 7.7 / 35.3 |
| 10–13 | 4.64 | 641 | 24 | 49.6 / 10.9 / 6.6 / 32.9 |
| 13–15 | 5.93 | 832 | 25 | 54.4 / 13.4 / 8.1 / 24.0 |
| 15–17 | 8.49 | 1220 | 28 | 57.3 / 10.9 / 6.7 / 25.1 |
| 17+ | 12.11 | 1833 | 30 | 61.7 / 11.2 / 5.1 / 22.0 |

这组数据直接决定了：类型权重、目标 NPS、以及「必须有多条判定线/动效」而不是一根静止的线。
难度选择也由这组 NPS 区间反推，而不是让用户凭感觉选。

## 5. 硬规则（下载前逐条校验）

分两层：**格式合法**（`validateChart`，不合法禁止下载）与**可玩性**（`auditPlayability`，
error 禁止下载、warn 只提示）。

| # | 规则 |
|---|---|
| R1 | 音符吸附到可读时值 1/1 · 1/2 · **1/3** · 1/4 · **1/6**；层级按代价选，简单读法优先 |
| R2 | 第一个 note ≥ 2 拍（lead-in） |
| R3 | 最后一个 note 的 start ≤ 总拍数 − 1 拍 |
| R4 | 同一只手最小间隔 = 难度 `minGap`（**free 模式也查**，默认 0.12 拍） |
| R5 | 同轨 Hold 与下一个 note 不重叠 |
| R6 | 同一时刻 ≤ `maxChord` 个音符 |
| R7 | 类型只允许 Tap / Hold / Flick / Drag |
| R8 | 2 指自由分散：左右手各半屏；同一时刻最多 1 个 note；同侧连续 ≤ 6 |
| R9 | Hold 长度 0.25–2 拍，且 end > start |
| R10 | 同一音频 + 同一难度 → 逐字节可复现 |
| R11 | **音符必须来自真实的音频事件**；候选不够就少给，**绝不补造** |
| R12 | lead-in / 收尾 / 重叠 / 和弦 / 同手冲突 任一失败 → 禁止下载 |
| R13 | `META.offset` 必须是整数（Phira/RPE 解析要求 i32；本项目固定 0） |
| R14 | 只有一条主判定线（无装饰线、无段落动效） |
| R15 | ~~补位只使用非 Hold~~ **已删除**：补位机制整体移除（见 R11） |

### 可玩性审计项（`public/js/playability.js`）

| 代码 | 级别 | 判据 |
|---|---|---|
| `time-conflict` | error | 同一只手在同一时刻有两个音符 |
| `hold-overlap` | error | 长条与同手下个音符重叠 |
| `chord` | error | 同拍音符数 > `maxChord` |
| `lead-in` | error | 第一个音早于 2 拍 |
| `same-hand-gap` | warn | 同一只手间隔 < `minGap` |
| `density-spike` | warn | 0.2 秒窗口 NPS > 目标 × 2 |
| `density-sustained` | warn | 2 秒窗口 NPS > 目标 × 1.35 |
| `target-mismatch` | warn | 整曲平均 NPS 与目标偏离 > 35% |
| `same-hand-run` | warn | 同一只手连续 > 8 个（换气口算断开） |
| `long-stream` | warn | 连续 ≥ 16 个间隔 ≤ 1/4 拍，无换气口 |
| `unreadable-rhythm` | warn | > 5% 的音符不落在可读网格上（容差 0.035 拍） |

> ⚠ **密度一律按时间窗算，不按总数**。
> 10 秒 60 个音与 60 秒 360 个音 NPS 相同但手感完全不同。
> 所以除了瞬时峰，还要看 2 秒峰与同侧连续负担。

`validateChart(chart)` 返回 `{ok, violations, metrics}`；页面在生成后、显示下载前执行。
失败时隐藏下载按钮并显示前 3 条违规。

## 7. 不用 Rana / 不接模型

Rana 是 B 站「小百合-official」的 Transformer 踩音模型：作者说「按设定开源」但代码未公开、
权重走 QQ 群、许可证不明确，因此本项目不集成。若以后有合规的踩音 points 输出，
可以用 `phm/audio2pez --from-points notes.json` 走另一条规则排谱路径。

## 9. 已知边界

- BPM/拍点来自通用谱通量 + 自相关，复杂曲风可能偏 1–2 BPM；页面会显示实际提取值。
- 判定线动效是规则化的（段落级 move/rotate/alpha），不是逐帧手工编排；视觉复杂度和真实谱面仍有差距。
- 规则保证结构合法与可玩性下限，不保证「好听」；质量取决于音频的拍点/能量。
- 只输出 RPE v160；Phira 其它格式未覆盖。
- `.pez` 建议在真 Phira 客户端导入验证一次；不同版本若有字段差异按报错修。
