# 事故记录 · 2026-11-23 · 数据查询全线不可用

> 状态：**部分未修复**（数据库侧需人工处理）
> 影响：依赖数据库的查询功能；**算定数不受影响**

---

## 一、现象

BetterStack 七个监控同时转红，状态页显示全线故障。
但站点首页、`/app`、`/chart/*`、`/status` 全部返回 **200**。

人工复测发现三种响应并存：

| 端点 | 返回 |
|---|---|
| `/api/v1/meta` | 200（不查库） |
| `/api/v1/charts/22681` | **429** rate_limit_exceeded |
| `/api/v1/analyses/probe` | **503** `db:false` |

BetterStack 的事件原因也分成两类：`Status 503`（4 个）与
`Timeout (no headers received)`（2 个）。

---

## 二、根因（两层，互相放大）

### 层 1：数据库算力额度用尽（致命，需付费或等待）

直连数据库返回：

```
53000  Your account or project has exceeded the quota.
```

进入 Neon 控制台确认（2026-11-23 实测）：

| 项 | 值 |
|---|---|
| 项目 | `tiny-boat-40056551`（AWS ap-southeast-1） |
| 分支 | `production` / `br-winter-morning-azdswpxk` |
| 计划 | Free（$0） |
| 包含 | 1 GB 存储 · 2 CU 上限 · **100 compute hours** · 10 分支 |
| 已用 | **110.09 CU-hrs** ← 超的就是这个 |
| 存储 / 网络 | 0.05 GB / 0.35 GB（都不是瓶颈） |
| 恢复时间 | **7 天后**（控制台横幅原文：`Resets in 7 days`） |

控制台横幅：`Limit reached — Monthly compute allowance used (100 CU-hrs).`

**这不是代码问题，也不是数据太多。** 用尽的是「数据库运行时长」这一项。

#### 为什么一个月会烧掉 100 小时

免费计划的挂起策略**不可修改**（`Settings → Postgres → Compute defaults`）：

```
Compute size: 0.25 ↔ 2 CU
Scale to zero: 5 minutes (default)
「Upgrade to control compute size and scale to zero」
```

即：只要 5 分钟内有任何一次查询，数据库就保持运行。单次唤醒的成本：

```
0.25 CU × 5 min = 0.0208 CU-hrs
100 CU-hrs ÷ 0.0208 ≈ 4800 次唤醒/月
```

而修复前是 7 个监控 × 4 区域 × 每 5 分钟 = **每小时 336 次探测**，
且 7 个探针**全部会查库**（`/api/v1/charts` 要读定数缓存）。

336 次/小时 × 730 小时 ≈ 24 万次 —— 远超 4800 次的上限。
**监控探针自己是这次额度耗尽的主因。**

**可选处理**：
1. 等 7 天自动重置（免费）
2. Billing → `Increase your limits`，**+$5/月** 把算力提到 250 小时（存储 5×、网络 5×）
3. 升级 Launch 计划（按量付费）

⚠ 涉及付款的选项**必须由站点主人本人操作**，脚本无法也不应代为扣款。

### 层 2：探针把自己的额度打爆（已修复）

站点匿名额度 `apiAnonHour = 100`，**按 subject（IP）计**。
BetterStack 有 4 个探测区域（eu / us / as / au），7 个监控 × 每 300 秒
⇒ 每区域约 **84 次/小时**。

84 距 100 只剩 16 次余量。真实访客进来就溢出 → 429。

更糟的是**恶性循环**：
1. 数据库挂了 → 探针收到 503/超时 → 判定为宕机
2. 监控持续探测，其中 `/analyses/probe` **每次都会查库**
3. 在 Neon 免费计划的自动挂起机制下，每次探测都唤醒一次数据库
4. 数据库越被唤醒，计算额度消耗越快 → 更难恢复

---

## 三、已做的修复

| 项 | 改动 | 依据 |
|---|---|---|
| 全部探针区域 | 4 区域（eu/us/as/au）→ **仅 us** | 唤醒次数直接降 4 倍 |
| 全部探针频率 | → **1800s** | BetterStack 平台上限就是 1800s（`[30,45,60,120,180,300,600,900,1800]`），再长会被 422 拒绝 |
| 监控数量 | 7 个 → **2 个活跃**（暂停 5 个） | 6.7 次/小时是免费额度的硬上限，7 个做不到 |
| 保留 | `P.H.M. 接口`、`P.H.M. 分析链路` | 前者是核心 API，后者是唯一真正检查库的 |
| `tools/fix-monitors.mjs` | 增加频率修正能力 | 原来只改 URL |

**改后实测**：2 个活跃 × 2 次/小时 × 730 小时 ≈ 2920 次/月
⇒ 探针消耗 ≈ **60.8 CU-hrs/月**，留约 39 小时给真实访客。

⚠ 被暂停的 5 个监控**没有删除**，随时可在 BetterStack 面板恢复；
但在免费计划下恢复就意味着重新超限，除非同时改用付费计划。

⚠ `scale to zero` 时间无法在免费计划下调短（界面明写需要 Upgrade），
所以「让数据库更早挂起」这条路走不通 —— 只能减少唤醒次数。

**没有做的**：给探针加 API Key。
理由：key 要存到第三方控制台，且走 key 额度 1000/h——
为了 7 个探针占用一把长期凭据，收益不抵风险。

## 四、影响范围（如实）

| 功能 | 状态 |
|---|---|
| 算定数（拖入谱包，浏览器本地算） | ✅ 正常 |
| 谱面包下载 | ✅ 正常 |
| 页面浏览 / 版本页 / 状态页 | ✅ 正常 |
| 谱面搜索、全库统计 | ❌ 不可用 |
| 玩家 / 谱师查询 | ❌ 不可用 |
| 按需分析（PoW 换分析） | ❌ 不可用 |
| 谱面详情页的「P.H.M. 定数」 | ⚠️ 降级（缓存读不到，需实时算） |

核心功能是纯前端计算 + 静态参照集（`ref-com.json` 2.1MB 仍可正常下载），
所以「算定数」这条主链路**没有受影响**。这是 2026-10-21 那次收敛决策的回报。

## 六、对外通告（已发布）

状态页报告 **id=1133648**，`aggregate_state=downtime`，7 个组件全部标记为受损。

标题（线上实际显示的这一句）：

> 数据查询服务资源受限，搜索/统计/玩家查询暂不可用（算定数不受影响）

### ⚠ 为什么只有标题、没有正文

BetterStack 的 status-reports API **不保存正文**。实测：
- `attributes` 只有 `title / report_type / starts_at / ends_at / status_page_id / affected_resources / aggregate_state`
- POST 时传 `message` → 静默丢弃（201 创建成功，但字段不存在）
- PATCH `message` → `422 invalid_attributes:["message"]`
- `/status-reports/{id}/status-updates` → 404（端点不存在）

所以**能写的只有标题**，结论必须一次说完。这也解释了 11-09 那两条历史通告
为什么标题里带着「（服务未中断）」——不是啰嗦，是唯一能写的地方。

```bash
BETTERSTACK_TOKEN=xxx node tools/incident.mjs --resolve 1133648
```
